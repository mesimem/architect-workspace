# Tech Stack: Boutique Travel Concierge

## Recommended stack

| Component | Recommended tech | Fit | Why | Learn more |
|---|---|---|---|---|
| Agent Dashboard | React + Vite (TypeScript) | 🟢 | This is a login-only tool for your own agents, not a public website, so you don't need the extra machinery (like search-engine optimization) that bigger frontend frameworks add. | `Explain React + Vite to me like I'm new to frontend frameworks, using my Boutique Travel Concierge Agent Dashboard as the example. What would the screens actually look like?` |
| Client & Itinerary Service | Node.js + Express (TypeScript) | 🟢 | A straightforward service that saves and fetches client and itinerary records — this pairs naturally with a React frontend since both speak the same language (TypeScript). | `Explain Node.js and Express to me like I'm new to backend services, using my Client & Itinerary Service as the example. What would a "create itinerary" request look like end to end?` |
| Booking Orchestration Service | Node.js + Express (TypeScript), using PostgreSQL transactions and an idempotency-key table | 🟡 | This is the piece that must never double-book or double-charge, so it checks "have I already done this booking?" before touching anything, using your database's built-in ability to make several steps succeed or fail together as one unit. | `Explain database transactions and idempotency keys to me like I'm new to reliability engineering, using my Booking Orchestration Service as the example. Walk me through what happens if the payment step times out.` |
| Marketing Content Service | Anthropic Claude API (Claude Sonnet 5) | 🟢 | This drafts social posts and surfaces insights for an agent to review and approve — it never publishes on its own, which matches an AI tool you review rather than one you trust blindly. | `Explain the Claude API to me like I'm new to AI tools, using my Marketing Content Service as the example. How would I ask it to draft a post and get back something an agent can edit?` |
| Bookkeeping Service | Node.js + Express (TypeScript) | 🟢 | It reads confirmed bookings and payments and turns them into ledger entries and reports — ordinary record-keeping logic, no special technology needed beyond what the rest of the backend already uses. | `Explain how a bookkeeping/reporting service is usually structured, using my Bookkeeping Service as the example. What would an invoice record look like in the database?` |
| Agency Database | PostgreSQL 16 | 🟢 | Client profiles, itineraries, bookings, and financial records all need strict rules (like "never book the same seat twice") that this type of database is specifically built to enforce. | `Explain PostgreSQL to me like I'm new to databases, using my Boutique Travel Concierge as the example. What tables would I actually have, and how would the booking table prevent duplicates?` |
| Supplier APIs | Direct API integration per supplier (e.g. Duffel for flights), with a manual confirmation fallback for suppliers without an API | 🔴 | Major flight and hotel suppliers have modern booking APIs, but boutique safari and luxury tour operators very often don't — some still confirm bookings by phone or email, which the Booking Orchestration Service's "reserve automatically" design doesn't account for. | `Explain what it takes to integrate with travel supplier APIs (flights, hotels, tour operators) to me like I'm new to third-party integrations, using my Boutique Travel Concierge as the example. What do I do about suppliers with no API at all?` |
| Payment Processor | Stripe | 🟢 | Stripe is built to charge a client once and confirm it once, which is exactly the "no payment errors" guarantee this project's day-one requirement demands, and it keeps you out of the business of handling raw card numbers. | `Explain Stripe to me like I'm new to payment processing, using my Boutique Travel Concierge as the example. How would it plug into my Booking Orchestration Service so a retry never double-charges a client?` |
| Social Platforms | Meta Graph API (Facebook & Instagram) | 🟡 | This is the one official way to publish approved posts and pull back engagement data from the two platforms your idea specifically names. | `Explain the Meta Graph API to me like I'm new to social media integrations, using my Marketing Content Service as the example. What does the approval-then-publish flow look like in practice?` |

## Fit rating key
- 🟢 great fit — matches this idea's scale and needs well; no meaningful downside for a boutique agency running this internally.
- 🟡 good fit — works, but there's a real tradeoff worth knowing before you commit.
- 🔴 consider carefully — likely to cause friction because it doesn't fully match how this specific idea's suppliers actually operate.

## Notes
- Agent Dashboard, Client & Itinerary Service, Booking Orchestration Service, and Bookkeeping Service are all recommended as one shared Node.js + TypeScript codebase style (even if split into separate deployable services later) — this keeps a small team from having to context-switch between languages for what is, day one, a handful of internal-facing services.
- The 🔴 on Supplier APIs isn't a technology problem — no library fixes it. It's a process problem: the architecture's "reserve inventory with SupplierAPIs" step needs a defined fallback (an agent manually confirms and marks the booking reserved) for any supplier that can't be called programmatically, or the "no double-booking" guarantee silently doesn't apply to those bookings.
- Least confident: the Booking Orchestration Service call — Postgres transactions plus an idempotency table is the simpler choice and fits a boutique agency's volume, but if booking volume grows or supplier calls start needing long asynchronous retries, this may need to become a dedicated workflow/orchestration layer later. Flagged 🟡 rather than 🟢 for that reason.
