Week 4 Deep Dive · Software Engineer

Software Engineer Field Guide

You are not being trained to write production code. You are being trained to direct it, evaluate it, and sign your name under it. This guide carries the twenty percent of software engineering that makes those three acts defensible — and then hands you the seven documents that turn judgement into a repeatable gate.

What this guide is

A knowledge base, not a course. Every topic is a standalone article you can find by search, quote in a meeting, or paste into a prompt. Every one of the seven deliverable documents is a real artifact — written out in full, not summarised — that you can download as a branded HTML file, save as a PDF, and in the tabular cases open in Excel.

The three jobs of an AI Solution Architect over code

Job 1 · Direct

Turn a business intent into a specification precise enough that a competent generator — human or model — produces the right thing. Vague direction is the root cause of most bad AI output. DOC-01 and DOC-02 are the instruments.

Job 2 · Evaluate

Read code you did not write and decide whether it does what was asked, fails safely, and can be changed next quarter without fear. The review lens and DOC-04 make that judgement repeatable rather than moody.

Job 3 · Approve

Attach your name to a claim that the change is safe to run in production. Approval is an evidence decision, never a vibe. DOC-07 defines the evidence; DOC-05 produces it.

The one rule that outranks the rest

Large language models are probabilistic. Production systems must be deterministic. Your entire job at the code boundary is to wrap probabilistic generation in deterministic proof: typed contracts, explicit failure paths, idempotent side effects, and tests that fail loudly when behaviour drifts. If a change cannot be proven, it cannot be approved — regardless of how confident the model sounded.

Foundations · 01

Why software engineering exists

Programming is getting a computer to do something once. Software engineering is getting a system to keep doing the right thing while the requirements, the team, the data volume and the surrounding world all change underneath it.

Nothing in software engineering exists for elegance. Every practice in this guide was invented as a scar-tissue response to a specific, expensive failure. Understanding which failure a practice answers is what lets you apply it with judgement instead of ceremony.

Each practice is a response to a failure
PracticeThe failure it preventsWhat it costs you
Technical design documentBuilding the wrong thing correctly. Six weeks of clean code solving a problem nobody had.Two to six hours of thinking before any code is written.
ModularityA one-line change to tax logic breaks the printing of receipts, because both live in the same 3,000-line file.More files, more indirection, more naming decisions.
Interfaces and contractsTwo teams integrate on Friday and discover they disagreed about whether the price field is cents or dollars.Types must be written and kept honest; changes become negotiations.
Version control and reviewNobody knows why line 402 exists, who changed it, or whether reverting it is safe.Review latency; a second person's attention on every change.
Automated testsA fix in March silently re-breaks a behaviour that was fixed in January.Test code is real code: it must be written, read and maintained.
Explicit error handlingAn outage looks like a slow page for three hours because a timeout was never set and a failure was swallowed.The unhappy path is often larger than the happy path.
IdempotencyA retried request charges a customer twice, or emails them the same order confirmation nine times.A key must be threaded through every side-effecting call.

Cost of change is the real metric

A codebase's health is not how fast it was written; it is how expensive the next change is. Well-engineered systems have a flat cost-of-change curve: the hundredth feature costs roughly what the tenth cost. Badly engineered systems have an exponential curve, and the symptom arrives as a sentence rather than a chart — "we can't ship that this quarter, it touches the pricing module."

Why this matters more, not less, with AI generating the code

A model can produce a plausible 400-line service in twelve seconds. That collapses the cost of writing code to nearly zero and leaves every other cost untouched: reading it, integrating it, operating it at 7pm on a Friday, and changing it in nine months. Generation speed has shifted the bottleneck decisively toward specification and verification — the two ends of the pipeline that are your job.

The specific hazard of generated code

AI-written code is locally excellent and globally naive. It is well-formatted, idiomatic and confident, which makes it read as trustworthy. What it does not know is your system: which table already holds this data, which service already owns this responsibility, what your timeout budget is, or that retrying this call twice will double-charge a customer. Those are precisely the defects a checklist catches and a skim does not.

Self-check
  • Can you name the failure that each of the seven practices above prevents, without re-reading the table?
  • For the last thing you asked an AI to build: what would have gone wrong on the second run?

The worked example

Every document in this guide is written against one invented but believable feature, in one industry: restaurant operations. Abstractions are easy to nod along with and impossible to apply. A single concrete case forces the guide to be specific enough to argue with.

Estate84 locations, 3 brands

The business situation

Harborview Grill Group runs 84 fast-casual restaurants across three brands. Roughly 41 percent of revenue now arrives through digital channels: the Harborview mobile app, the web ordering site, in-store kiosks, and three third-party delivery marketplaces. When a guest places a digital order, the system currently tells them "ready in about 20 minutes" — a constant, hardcoded in 2019, identical at 3pm on a Tuesday and 7:15pm on a Friday.

The consequences are measurable and expensive:

  • Guest experience. At peak, real ready times reach 38 minutes. Guests arrive at 20 minutes, wait in a crowded lobby, and rate the visit two stars for a kitchen that performed normally.
  • Food quality. Off-peak, orders are ready in 9 minutes and sit under a heat lamp for 11. Fries are the most-complained-about item in the estate.
  • Marketplace penalties. Two of the three delivery partners levy a fee when a courier waits more than 6 minutes past the quoted time. Last quarter that cost 96,400 dollars.
  • Labour churn. Store managers manually pause digital ordering during rushes, which suppresses revenue and is applied inconsistently across the estate.

The feature: Quoted Ready Time (PTPS)

The Prep-Time Promise Service replaces the hardcoded 20 minutes with a per-order, per-location quoted ready time, calculated at the moment of ordering from the actual composition of the basket and the real-time state of that kitchen. A machine-learning model predicts the wait; a deterministic heuristic stands behind it; the promise the guest sees is always produced by explicit, auditable rules.

In scope
  • Synchronous quote API for app, web, kiosk and marketplace order flows
  • Basket-aware prep estimation using per-item prep profiles
  • Live kitchen load read from the Kitchen Display System (KDS)
  • ML wait prediction with a deterministic heuristic fallback
  • Quote persistence and a full audit trail of every promise made
  • Accuracy telemetry: quoted versus actual, by location and daypart
Explicitly out of scope
  • Training or retraining the prediction model (owned by the Data Science team)
  • Courier dispatch and delivery-leg estimation
  • Changing menu prices or the promotions engine
  • Any change to the KDS hardware or its firmware
  • Automatic pausing of digital ordering (phase 2, requires ops sign-off)

Why this example is well chosen for an AI architect

It is a hybrid feature, and hybrids are where architects earn their keep. There is a probabilistic component (a model that predicts a number and will sometimes be wrong, unavailable, or slow) sitting inside a deterministic business promise (a time shown to a guest, relied on by a courier, and used to compute a penalty). The engineering question is not "is the model good" — it is "what does the system do when the model is bad, and can we prove it." That question generates every contract, fallback, timeout, test case and review check in the documents that follow.

The 20 percent · 01

Technical design documents

A technical design document is the artifact that makes disagreement cheap. Arguing about a paragraph costs an hour. Arguing about a deployed service costs a quarter.

A TDD is not documentation of what was built — that is a different, lesser genre. A TDD is a decision record written before the decision is expensive to reverse. Its readers are: the engineer who will implement it, the architect who will approve it, the on-call engineer who will be paged by it at 2am, and the person who inherits it in eighteen months.

The seven sections that earn their place

SectionQuestion it answersFailure if omitted
1. Context and problemWhat is broken, for whom, and how do we know?The team optimises a metric nobody asked for.
2. Goals and non-goalsWhat will be true when this ships, and what deliberately will not?Unbounded scope; the project never ends.
3. Chosen approach and alternativesWhich option, and why not the other two?The same debate is reopened every three months by every new joiner.
4. Module breakdownWhat are the parts, and what is each one responsible for?Responsibilities pool in one file; the "god service" is born.
5. Data modelWhat is stored, keyed how, and what is the source of truth?Duplicate state, disagreeing reports, a migration under fire.
6. Main flow sequenceIn what order does what call what, with which timeouts?Latency budget is discovered in production.
7. Risks and trade-offsWhat are we knowingly accepting, and what is the mitigation?Known risks are experienced as surprises.

Length discipline

Target four to eight pages for a feature of this size. A forty-page design document is not thorough; it is undecided. If a section cannot be written, that is the signal — you have found the thing you do not yet understand, and it is far cheaper to find it here.

Using a TDD to direct AI

The module breakdown and data model sections of DOC-01 are the highest-value context you can give a code generator. Paste section 4 and section 5 into the prompt, name the one module you want written, and state the contract from DOC-02. Output quality moves from "plausible" to "reviewable" on that change alone, because you have removed the model's need to invent your architecture.

What "approved" means on a TDD

Your signature on a design document asserts four things, and only these four: the problem is real and correctly stated; the chosen approach is defensible against the stated alternatives; the failure paths are named rather than assumed; and every requirement is traceable to a module and a test. It does not assert that the design is optimal. Optimal is not a standard anyone can hold you to; defensible is.

The 20 percent · 02

Modularity & separation of concerns

A module should have one reason to change. Not one function, not one file — one reason. When you can state that reason in a single sentence with no "and" in it, the module is correctly drawn.

The test that settles most arguments

Write the module's responsibility as one sentence. If the sentence needs the word and, you are looking at two modules. Apply it to the worked example:

Fails the sentence test
// quoteService.ts  (1,240 lines)
// "Validates the request AND reads the menu
//  AND calls the KDS AND calls the model
//  AND applies buffers AND writes the row
//  AND publishes the event AND formats
//  the API response."
Seven reasons to change. A menu-schema change and a model-endpoint change now touch the same file, so they cannot be shipped or reverted independently.
Passes the sentence test
// promiseCalculator.ts  (96 lines)
// "Converts a base prep estimate and a
//  load factor into a guest-facing ready
//  time within policy bounds."

// kitchenLoadProbe.ts  (118 lines)
// "Reports the current load of one
//  kitchen as a normalised factor."
One reason each. The ops team can change buffer policy without anyone touching KDS integration code.

Size targets as a smoke alarm

Numbers are not the goal; they are the alarm that makes you look. In this repository's house style: files target ~300 lines with a hard ceiling of 500; functions target ~50 lines with a ceiling of 100; a module exports 5 to 7 public symbols, ceiling 12. Crossing a ceiling does not mean the code is wrong — it means the next change to that file must split it before adding anything.

The AI-specific failure mode

Ask a model to "add marketplace support to the quote service" and it will, very competently, add 140 lines to the file you showed it. Models optimise for the local edit and have no stake in your file's coherence. Modular boundaries are the architect's responsibility, and they must be stated in the prompt. Name the file the code goes in, and say what that file is not allowed to do.

Coupling and cohesion, without the jargon

  • High cohesion — things inside a module belong together and are usually read together. Good.
  • Low coupling — a module knows the least possible about others: their interface, never their internals. Good.
  • The circular import — A imports B, B imports A. This is never a naming problem; it is a missing third module C that both should depend on. In PTPS, that module is contracts/quoteTypes.ts, which holds shared types and imports nothing.
The 20 percent · 03

Interfaces & contracts

An interface is the shape. A contract is the shape plus the promises: what must be true going in, what is guaranteed coming out, what can fail and how, and what happens twice if you call it twice.

Most integration failures are not coding errors. They are two correct implementations of two different assumptions. The contract is where the assumption is written down once, in a place a compiler and a test can both check.

The five parts of a complete contract

PartWhat it statesPTPS example
InputsTypes, units, ranges, required versus optional, and validation owner.basket: BasketLine[], 1 to 60 lines; quantity integer 1 to 40.
OutputsExact shape and units of a successful result. No optional fields the caller must guess at.quotedReadyMinutes: number — whole minutes, always 5 to 75.
ErrorsThe enumerated, named failures. Which are retryable, which are terminal.ValidationError, LocationClosedError, UpstreamUnavailableError.
Side effectsWhat changes in the world, and under which idempotency key.One row in quotes, keyed on idempotency_key; one event published.
TimingLatency budget and the timeout the caller should apply.p95 under 400 ms; caller timeout 800 ms; model sub-call capped at 120 ms.

A real contract from the example

// contracts/quoteTypes.ts  --  imports nothing; the shared vocabulary.

export interface QuoteRequest {
  locationId:      LocationId;        // branded string, "HGG-" + 4 digits
  channel:         OrderChannel;      // 'APP' | 'WEB' | 'KIOSK' | 'MARKETPLACE'
  basket:          readonly BasketLine[]; // 1..60 lines, non-empty
  requestedAtUtc:  IsoTimestamp;      // caller's clock, ISO-8601 with offset
  idempotencyKey:  IdempotencyKey;    // UUID v4, supplied by the caller
  correlationId:   CorrelationId;     // UUID v4, propagated to every log line
}

export interface QuoteResult {
  quoteId:              QuoteId;
  quotedReadyMinutes:   number;   // WHOLE MINUTES. Never seconds. 5..75 inclusive.
  quotedReadyAtUtc:     IsoTimestamp;
  confidence:           'HIGH' | 'MEDIUM' | 'LOW';
  estimationSource:     'MODEL' | 'HEURISTIC' | 'FLOOR_CLAMP' | 'CEILING_CLAMP';
  modelVersion:         string | null;   // null iff source !== 'MODEL'
  replayed:             boolean;          // true = served from idempotency cache
}

/**
 * CONTRACT
 *  Pre  : request passes QuoteRequestSchema; location exists and is open.
 *  Post : returns QuoteResult, or throws exactly one of the errors below.
 *  Errors:
 *    ValidationError        (400, terminal)  malformed or out-of-range input
 *    LocationClosedError    (409, terminal)  location not trading at requestedAtUtc
 *    UnknownMenuItemError   (422, terminal)  a basket line is not on that menu
 *    UpstreamUnavailableError (503, retryable) KDS unreachable AND no cached load
 *  Side effects: exactly one `quotes` row per idempotencyKey; one quote.created event.
 *  Timing: p95 < 400 ms. Internal deadline 700 ms, then FLOOR_CLAMP is returned.
 *  Idempotency: same idempotencyKey within 15 minutes returns the SAME quoteId
 *               with replayed=true. No new row, no second event.
 */
export interface QuoteOrchestrator {
  quote(request: QuoteRequest): Promise<QuoteResult>;
}
Why quotedReadyMinutes and not time

The unit is in the name. Every field that carries a magnitude — money, duration, distance, weight — names its unit in the identifier: totalCents, prepSeconds, quotedReadyMinutes. This single convention eliminates an entire family of production incidents that no type system catches, because number and number compile fine whether one of them was seconds.

Contract strength test

A contract is strong only if breaking it breaks a test. Ask: could someone change this module's behaviour in a way that damages a caller, while every test still passes? If yes, the contract is decorative. In the example, the guard is UNIT-16, which asserts the 5-to-75 clamp, and INT-09, which asserts that a replayed key returns the same quoteId and creates no second row.

Breaking versus non-breaking changes

ChangeVerdictHandling
Add an optional output fieldSafeShip it. Callers ignoring it are unaffected.
Add an optional input with a defaultSafeDocument the default in the contract comment.
Add a value to an output unionCarefulCallers switching exhaustively will break. Announce; check consumers.
Narrow an accepted input rangeBreakingRequires consumer updates in the same change, or a version.
Rename or retype any fieldBreakingDeprecation path, or one coordinated change updating all callers.
Change a unit while keeping the nameBreakingNever do this. Introduce a new, correctly named field and retire the old one.
The 20 percent · 04

Clean code & naming

Code is read far more often than it is written. Clean code is not a style preference; it is a decision to spend ten seconds now so that the next reader — frequently you, with the context gone — spends ten seconds instead of ten minutes.

Naming: the highest-return skill in the discipline

A name should answer what and in what unit, and should not require the reader to open another file. Four rules cover nearly every case:

  1. Reveal intent, not mechanism. activeLocationsForBrand beats filteredList2. The name describes the contents, not how they were obtained.
  2. Carry the unit. prepSeconds, totalCents, quotedReadyMinutes. Never a bare duration, amount or size.
  3. Booleans read as assertions. isKitchenOpen, hasUnknownItems, shouldUseHeuristic. A boolean named status or flag is a defect waiting to happen.
  4. Functions are verb phrases; the verb tells you the cost. get* is cheap and local. fetch* crosses the network and can fail. calculate* is pure. persist* writes. A reader should be able to guess whether a line can throw from the verb alone.

Functions: one level of abstraction

A function should read as a paragraph at a single altitude. Mixing altitudes — a policy decision next to a byte-level string operation — is what makes a 90-line function feel like 300.

Single altitude: the function reads as the algorithm
async quote(request: QuoteRequest): Promise<QuoteResult> {
  const existing = await this.quotes.findByIdempotencyKey(request.idempotencyKey);
  if (existing) return asReplayed(existing);

  const basePrep  = this.catalog.calculateBasePrepSeconds(request.basket);
  const load      = await this.loadProbe.readLoadFactor(request.locationId);
  const estimate  = await this.waitEstimate(request, basePrep, load);
  const promise   = this.calculator.toGuestPromise(estimate, request.channel);

  const saved = await this.quotes.persist(promise, request);
  await this.events.publishQuoteCreated(saved, request.correlationId);
  return saved;
}
Nine lines. Every line is a named step at the same altitude, so the shape of the algorithm is visible without reading any of the parts. Details live one level down, where they are individually testable.

Comments: the why, never the what

A comment restating the code is noise that goes stale. A comment recording a decision, a constraint, or a piece of non-obvious domain knowledge is the most valuable text in the file.

Noise
// add 90 to the prep time
prepSeconds += 90;
Restates the line and explains nothing. The magic number survives.
Signal
// Fryer batching: orders containing any fried item
// wait for the next basket cycle. Measured mean
// across the estate is 90s (Ops study, 2026-03).
prepSeconds += FRYER_BATCH_CYCLE_SECONDS;
Records domain knowledge no reader could infer, cites its source, and names the constant.
Where AI-generated code needs the most editing

Models produce comments prolifically and generically — // loop through the items on every loop. They also default to placeholder names (data, result, handler, utils.ts) because they lack your domain vocabulary. Two instructions in the prompt fix most of this: "use the names in the attached contract file verbatim" and "comment only non-obvious decisions and cite the source of any constant."

The 20 percent · 05

Version control & code review

Version control is the system of record for why, not just what. Code review is the moment a change stops being one person's opinion and becomes the team's shared position.

The four things version control gives you

  • Reversibility. Any change can be undone as a discrete unit — which is only true if commits are coherent. A commit called "fixes" containing three unrelated changes cannot be partially reverted.
  • Attribution. Every line has an author, a date, and a message. git blame on a strange line should surface a reason, not a shrug.
  • Isolation. Work in progress does not destabilise what is running in production.
  • An audit trail. For a regulated or contested change — and a quoted time that drives a marketplace penalty is contested — the history is the evidence.

Commit messages that survive contact with the future

feat(ptps): clamp quoted ready time to policy bounds

5 minutes minimum, per the Ops floor study of 2026-03-14.

Requirement: REQ-05
Tests: UNIT-16, UNIT-17

The subject line is a sentence in the imperative under 72 characters. The body answers why, not what — the diff already says what. Requirement IDs, test IDs and assumptions are recorded because in nine months this message is the only surviving explanation.

Code review is not a spelling check

A reviewer answers four questions, in this order. Stopping at the first is the most common review failure:

OrderQuestionWhat a weak review does instead
1Is it correct? Does it do what the requirement asked, including at the boundaries?Confirms it looks like code that would work.
2Does it fail safely? Timeouts, retries, no silent catches, idempotent side effects.Skips the catch blocks entirely.
3Can it be changed? Single responsibility, no new circular dependency, tested behaviour.Approves because the change is small.
4Is it consistent? House naming, structured logs, no secrets, no stray any.Spends the whole review here, on formatting.
Review size is the strongest predictor of review quality

Defect-detection rate collapses beyond roughly 400 changed lines. A 900-line pull request does not get a review; it gets an approval. This is why DOC-06 caps PR size at 400 lines of production code and treats "split this" as the standard response to anything larger. With AI generating code, the temptation is the opposite direction — the model will happily produce 1,200 lines at once, and the architect's discipline is to demand it in slices that a human can actually hold in mind.

The 20 percent · 06

The testing pyramid

Tests are not proof that code is correct. They are proof that specific behaviours you care about are still true. The pyramid decides where each behaviour is cheapest to keep true.

What belongs at each tier

TierBelongs herePTPS example
UnitPure logic with no I/O: calculations, clamps, formatters, validators, prompt builders, mappers.toGuestPromise() clamps 2 minutes up to 5 and tags FLOOR_CLAMP. Runs in 0.4 ms.
IntegrationTwo or more real components across a boundary: route plus schema plus repository, with external systems stubbed.POST /v1/quotes twice with one idempotency key creates one row and returns replayed: true.
End-to-endOnly the critical user journeys, through the real interface.A guest builds a basket in the app, submits, and sees a ready time consistent with the API response.

The four mandatory test types per feature

Happy-path-only coverage is the most common form of incomplete work, and the easiest to mistake for done. Every shipped feature needs all four:

1. Happy path

The documented usage works as specified. A 3-item basket at a normally-loaded location returns a plausible quote. UNIT-07, E2E-01

2. Failure path

A dependency is down, slow, or returns nonsense. Model times out, KDS returns 503, model returns a negative number. UNIT-21, INT-06, INT-07

3. Boundary cases

Empty, maximum, one-off-the-edge. Zero-line basket, 60-line basket, 61-line basket, quantity 0, quantity 41, closing minute. UNIT-16..20

4. Idempotency

The same operation run twice leaves the same end state and fires no duplicate side effect. INT-09, INT-10

Tests assert behaviour, not implementation

Asserts implementation
expect(calc.applyBuffer).toHaveBeenCalledTimes(2);
expect(calc._internalCache.size).toBe(1);
Passes when the behaviour is wrong; fails on a harmless refactor. This test makes the code harder to change, which is the opposite of its purpose.
Asserts behaviour
// UNIT-16
it('clamps an implausibly low model estimate to the 5-minute floor', () => {
  const r = toGuestPromise({ seconds: 120, source: 'MODEL' }, 'APP');
  expect(r.quotedReadyMinutes).toBe(5);
  expect(r.estimationSource).toBe('FLOOR_CLAMP');
});
Survives any refactor that preserves the promise. Fails precisely when the guest-visible behaviour changes. The test name states the rule.
The tests AI writes, and the tests it does not

Models are strong at the happy path and at mechanical boundary enumeration. They are weak at the failure paths that matter, because those require knowing your dependencies' real behaviour — that your KDS returns HTTP 200 with an empty body when a store's tablet is asleep, for example. Specify the failure cases yourself. The reliable prompt shape is: "write tests for these seven named cases," with the cases taken from DOC-05, rather than "write tests for this file."

The 20 percent · 07

Error handling

Design the failure path before the happy path. In a system that talks to a machine-learning model, a kitchen display tablet and a payments provider, the unhappy path is the system. The happy path is the easy ten percent.

Four questions every external call must answer in writing

#QuestionPTPS answer for the model call
1What happens if this fails?Fall through to HeuristicWaitEstimator; tag the result estimationSource: 'HEURISTIC' and confidence: 'MEDIUM'. The guest still receives a time.
2Will it retry, and how?One retry on connection error or HTTP 503 only, after 40 ms. Never on 4xx. Total model budget 120 ms including the retry.
3What if retries are exhausted?Circuit opens after 5 failures in 60 seconds; the model is skipped entirely for 120 seconds. A model.circuit_open event pages the on-call data engineer, not the ordering team.
4What is explicitly not handled?A model that responds fast with a confidently wrong number inside the plausible range. Detection is out of band, via the accuracy telemetry in QuoteEventPublisher, not in the request path.

Question 4 matters as much as the first three. Naming the failures you are not handling converts an unknown risk into an accepted one — and an accepted risk can be monitored, budgeted and revisited. An unknown one can only surprise you.

Forbidden patterns

Silent swallow — a production defect

  load = await kds.getLoad(locationId);

// computes NaN minutes and quotes "in

Every symptom is downstream of the cause, so the outage is unreadable. This pattern is a blocking review finding, no exceptions.
Classified, logged, degraded

             location_id: locationId, correlation_id: cid,
             outcome: 'partial', fallback: 'last_known_snapshot' });

  if (!load) throw new UpstreamUnavailableError('kds', { cause: err });
}
Classified error, structured log with a correlation ID, a deterministic fallback, and a loud throw when even the fallback is unavailable. Nothing is guessed and nothing is hidden.
  • Empty catch blocks. Always a defect. If a failure is genuinely ignorable, the catch must say so in a comment and still log at debug level.
  • Catch and re-throw without context. Loses the error class and the correlation ID, which are the only two things that make an incident traceable.
  • Catching the base Error when a specific class is expected. Masks the root cause and turns a validation bug into a mysterious 500.
  • Unbounded retry. A retry loop with no cap converts a brief upstream blip into a self-inflicted denial of service.
  • No timeout. Every outbound HTTP, database and queue call carries an explicit timeout. A hanging call holds a connection, and enough of them take the service down without a single error being logged.

The 20 percent · 08

DRY and SOLID, lightly

These acronyms are useful as vocabulary for a review comment and harmful as doctrine. Each one names a real failure mode; each one, applied absolutely, produces its own.

DRY — don't repeat yourself

The rule is not "never type the same characters twice." It is every piece of knowledge has one authoritative home. Duplicated knowledge is the defect; duplicated text is often fine.

  • Real DRY violation. The 5-minute pickup floor appears as a literal 5 in the calculator, the API validator and the mobile app. Ops changes the policy to 6 and two of the three get updated. Fix: one exported constant, one owner.
  • False DRY violation. Two validators both check a string is non-empty. They look identical and answer different questions; merging them couples a menu rule to a customer rule for no benefit.
  • Practical threshold. Two occurrences may be coincidence. Three is a pattern — extract it. Extracting on the second occurrence is how premature abstractions are born, and a wrong abstraction costs more than the duplication it removed.

SOLID, in one line each, with the PTPS case

O · Open / closedExtend behaviour without editing working code.Adding a fourth marketplace adds a channel policy entry; it does not edit the calculator.

Which two actually pay rent

S and D carry almost all of the practical value, and they compound: single responsibility makes a module comprehensible, and dependency inversion makes it testable. Together they are the difference between a suite that runs in 900 milliseconds and one that needs a database, a stubbed KDS and four minutes. L earns its place the moment you have a fallback implementation — which PTPS does, and which is exactly where a subtly different unit or error class becomes a 2am incident. O and I are worth knowing so you can name a smell, and are not worth restructuring a working system to satisfy.

The over-application failure

Ask a model to "apply SOLID" to a 90-line service and you will receive six interfaces, three factories, an abstract base class and a dependency-injection container — for logic that had one caller. That is not engineering, it is costume. Abstraction is justified by a second real implementation or a demonstrated testing need, never by symmetry. When you see an interface with exactly one implementation and no test double, ask why it exists.

The 20 percent · 09

Technical debt

Technical debt is a deliberate, recorded decision to ship something suboptimal in exchange for time, with an understanding of what the interest costs. Everything else is not debt. It is just a mess.

The distinction that makes the term useful

Debt — legitimate, managed

"We are hardcoding the fryer batch cycle at 90 seconds for all 84 locations instead of measuring it per site. Ops estimates a 4-minute accuracy loss at the three highest-volume sites. Ticket PTPS-212 is raised to move it to per-location configuration in Q4."

Named, quantified, owned, ticketed, and with a repayment trigger.

Mess — no decision was made

"There's a 90 in the calculator. Nobody knows where it came from. It also appears as 85 in the mobile app and 90000 in a config file that may or may not be read."

Unnamed, unquantified, unowned. Cannot be prioritised, because nobody can state the cost of leaving it.

AI generation changes the debt profile

Models do not accumulate the classic debt of shortcuts and hacks — the code they emit is usually tidy. They accumulate duplication and drift: the fourth generated module reimplements retry logic the first three already had, in a fourth slightly different way. Nothing looks bad in any single review, and after two months there are four retry policies, three log formats and two definitions of the pickup floor. The counter-measure is an explicit shared-primitives layer named in DOC-03, and a review check that asks: does this already exist somewhere in the repository?

What you are actually approving

Your approval is not a claim that the code is good. It is a claim that you have evidence it does what was asked, it fails safely, and someone can change it later. Evidence means an artifact: a passing test that would fail if the behaviour regressed, a log line that would show the failure, a constraint that makes the duplicate impossible. If your only evidence is that the code looks right, you have read the code — you have not reviewed it.

Directing the AI

The quality of generated code is set almost entirely before generation, by how much of the specification you supplied. These are the four patterns that move output from plausible to reviewable.

Pattern 1 — Contract first, implementation second

Never ask for a module and its interface in the same request. Ask for the contract, review and correct the contract yourself, then ask for the implementation of that exact contract. The contract is short enough to read carefully, and every correction you make there propagates into hundreds of lines you no longer need to fix.

STEP 1

and contract comment for KitchenLoadProbe. No implementation. Include units in

STEP 2  (after you have corrected step 1)

  - Inject the clock and the logger; do not import them directly.
  - One structured log line per outcome, with correlation_id and duration_ms.
  - Target under 120 lines. Do not add functionality beyond the interface.

Pattern 2 — Name the tests, then ask for them

"Write tests for this file" produces happy-path coverage and a false sense of safety. Give the model the case list from DOC-05 by ID and description, and require one test per ID with the ID in the test name. You then verify the count, which is a five-second check.

Pattern 3 — State the negative space

Models fill silence with helpfulness. Every constraint you leave unstated becomes an invention: a new utility file, a new config key, a defensive default that hides a bug. Say what the code must not do.

Pattern 4 — Ask it to break its own work

After the implementation passes review, run one more pass in the adversarial direction. This is the cheapest defect-finding step available to you, because the model is genuinely good at enumerating failure modes when that is the explicit task rather than an afterthought.

The line you do not cross

The model can write the code, write the tests, and find its own defects. It cannot approve its own work — not because it lacks capability, but because approval is an accountability act and accountability cannot be delegated to a process that has no stake in the outcome. You sign. That is the job that does not move.

Chosen Isolates model risk behind a circuit breaker; keeps the guest-visible promise under deterministic rules; independently deployable and independently revertible. D Model-only, no heuristic path. Rejected The single most likely failure — model unavailable at peak, when load is highest — would leave the estate with no quote at all. Violates G-3. Availability of the promise must not depend on availability of the prediction.
Trade-off accepted with Option C

A synchronous call adds latency to the basket-review step and introduces a new service to operate. We accept a p95 budget of 400 ms and a new on-call surface in exchange for basket awareness and isolation of model risk. The mitigation for the latency cost is a hard internal deadline of 700 ms, after which the service returns a clamped heuristic quote rather than waiting.

5.1 MenuPrepCatalog — domain, pure

Responsibility. Converts a basket into a base prep-seconds estimate using per-item prep profiles.

// domain/menuPrepCatalog.ts

export interface PrepProfile {
  menuItemId:           MenuItemId;
  basePrepSeconds:      number;   // first unit
  perExtraUnitSeconds:  number;   // each additional unit of the same item
  requiresFryer:        boolean;
  stationCode:          string;
}

/**
 * CONTRACT  calculateBasePrepSeconds
 *  Pre   : basket has 1..60 lines; every quantity is an integer 1..40;
 *          every menuItemId has a profile in `profiles`.
 *  Post  : returns an integer >= 0 in SECONDS.
 *          Stations run in parallel, so total = max over stations of that
 *          station's serial time, NOT the sum of all items.
 *          If any line requiresFryer, exactly ONE fryer batch cycle
 *          (FRYER_BATCH_CYCLE_SECONDS) is added once, not per line.
 *  Errors: UnknownMenuItemError  - a line has no profile. Never defaults.
 *  Side effects: none. Pure function.
 *  Timing: O(lines). Under 1 ms for a 60-line basket.
 *  Idempotency: trivially idempotent; same input always same output.
 */
export function calculateBasePrepSeconds(
  basket:   readonly BasketLine[],
  profiles: ReadonlyMap<MenuItemId, PrepProfile>,
): number;

/** Returns the distinct station codes touched by a basket. Used by the
 *  model feature builder. Same preconditions and errors as above. */
export function stationsTouched(
  basket:   readonly BasketLine[],
  profiles: ReadonlyMap<MenuItemId, PrepProfile>,
): readonly string[];

Dependencies permitted: contracts/quoteTypes only. No I/O, no clock, no logger.

5.2 PromiseCalculator — domain, pure

Responsibility. Converts an estimate plus a channel into a guest-facing whole-minute promise inside policy bounds.

// domain/promiseCalculator.ts

export const MIN_QUOTED_MINUTES = 5;   // pickup counter floor, Ops 2026-03-14
export const MAX_QUOTED_MINUTES = 75;  // ops policy ceiling, not measured

export interface GuestPromise {
  quotedReadyMinutes: number;        // integer 5..75 inclusive, WHOLE MINUTES
  confidence:         Confidence;
  estimationSource:   EstimationSource;   // may be rewritten to a CLAMP value
  modelVersion:       string | null;
}

/**
 * CONTRACT  toGuestPromise
 *  Pre   : estimate.seconds is a finite integer >= 0.
 *          channel is one of the four OrderChannel values.
 *  Post  : 1. add the channel buffer (multiplier then addSeconds)
 *          2. convert to minutes, ROUNDING UP (never under-promise)
 *          3. clamp to [MIN_QUOTED_MINUTES, MAX_QUOTED_MINUTES]
 *          4. if clamped, estimationSource becomes FLOOR_CLAMP or
 *             CEILING_CLAMP and confidence is downgraded to LOW
 *          5. confidence for an unclamped HEURISTIC estimate is MEDIUM;
 *             for an unclamped MODEL estimate it is HIGH
 *  Errors: ValidationError if estimate.seconds is NaN, Infinity or negative.
 *          Never silently coerces. Never returns a non-integer.
 *  Side effects: none. Pure function.
 *  Timing: O(1), under 0.1 ms.
 *  Idempotency: trivially idempotent.
 */
export function toGuestPromise(
  estimate: PrepEstimate,
  channel:  OrderChannel,
): GuestPromise;

Dependencies permitted: contracts/quoteTypes only.
Contract held by: UNIT-15 to UNIT-20 (floor clamp, ceiling clamp, round-up never round-down, all four channel buffers, NaN rejection, confidence downgrade on clamp).

Why rounding up is in the contract

Rounding is a business decision disguised as arithmetic. Rounding 20.2 minutes down to 20 saves twelve seconds of perceived wait and costs a courier-wait fee whenever it tips the balance. The rule is stated in the contract so that an implementer cannot make it accidentally, and so that a reviewer can catch Math.round where Math.ceil belongs — a one-character defect worth thousands of dollars a quarter.

5.3 HeuristicWaitEstimator — domain, pure

Responsibility. Produces a deterministic wait estimate from base prep and load factor without calling the model.

// domain/heuristicWaitEstimator.ts

/**
 * CONTRACT  estimateHeuristicSeconds
 *  Pre   : basePrepSeconds integer >= 0; loadFactor 0.25..3.00.
 *  Post  : returns { seconds, source: 'HEURISTIC', modelVersion: null }.
 *          Formula, fixed and auditable:
 *            seconds = basePrepSeconds * loadFactor
 *                      + QUEUE_DRAIN_SECONDS_PER_OPEN_TICKET * openTickets
 *          Result is rounded to the nearest whole second.
 *          MUST be substitutable for the model path: same units, same
 *          bounds, same error classes. See Liskov note below.
 *  Errors: ValidationError on out-of-range loadFactor. Never clamps silently
 *          - a loadFactor of 9.0 means the probe is broken, and hiding that
 *          would hide the real defect.
 *  Side effects: none.
 *  Timing: O(1).
 *  Idempotency: trivially idempotent.
 */
export function estimateHeuristicSeconds(
  basePrepSeconds: number,
  loadFactor:      LoadFactor,
  openTickets:     number,
): PrepEstimate;

Liskov note. This function and the model path both satisfy the notional WaitEstimator role. Substitutability is a hard requirement: identical units (seconds), identical bounds, identical error classes. A fallback that returns minutes where the primary returns seconds is a 60x defect that no type checker catches, because both are number.
Contract held by: UNIT-21 to UNIT-23.

5.5 WaitPredictorClient — adapter

Responsibility. Calls the inference endpoint and returns a validated prediction or a classified error.

// adapters/waitPredictorClient.ts

export interface PredictionFeatures {
  locationId:        LocationId;
  basePrepSeconds:   number;
  loadFactor:        LoadFactor;
  openTickets:       number;
  stationsTouched:   readonly string[];
  basketLineCount:   number;
  localHourOfDay:    number;   // 0..23, store-local
  dayOfWeek:         number;   // 0..6, 0 = Sunday
}

/**
 * CONTRACT  predictWaitSeconds
 *  Pre   : every feature present and in range. The client does NOT
 *          fabricate defaults for a missing feature; a missing feature
 *          is a ValidationError raised before any network call.

 *          with CircuitOpenError in under 1 ms and no network is touched.

5.6 QuoteRepository — adapter

Responsibility. Persists and retrieves quotes under an idempotency key.

// adapters/quoteRepository.ts

export interface StoredQuote extends GuestPromise {

  locationId:        LocationId;
  channel:           OrderChannel;
  quotedReadyAtUtc:  IsoTimestamp;

/**
 * CONTRACT  QuoteRepository
 *
 *  findByIdempotencyKey(key, cid)
 *    Post  : returns the StoredQuote for that key if one was created within

 *

 *            optimisation; the constraint is the guarantee.

5.7 QuoteOrchestrator — application

1. How to use this checklist

  • Work the categories in order. A through I is ordered by how cheaply a check can reject the change. Category A can reject a pull request in ninety seconds without reading any logic.
  • Blocking means blocking. A blocking finding requires Request changes. It is not a comment, a nit, or a follow-up ticket. There are only nine of them precisely so that this rule can be absolute.
  • Automated checks come first. Anything a machine can verify — types, lint, coverage, dependency rules, secret scanning — runs in CI before a human looks. Human review time is spent on the checks a machine cannot make.
  • One reviewer, plus a second for blocking-category changes. Any change touching idempotency, authorisation, money, or the guest-visible promise needs two approvals.
Reviewer's opening move

Before reading the diff, read the PR description and answer one question: which requirement ID is this, and what evidence is offered that it works? If neither has an answer, stop and ask. Reviewing code whose purpose you have not established is how a reviewer ends up commenting on formatting for twenty minutes and missing a missing timeout.

Design and structure

What is a technical design document, and when do I actually need one?

A TDD is a decision record written before the decision becomes expensive to reverse. It carries seven sections: context and problem, goals and non-goals, chosen approach with alternatives, module breakdown, data model, main-flow sequence, and risks and trade-offs. Write one when a change introduces a new service, a new external dependency, a schema change, or a new failure mode — roughly, anything you could not revert in an afternoon. Target four to eight pages. A forty-page design document is not thorough, it is undecided. See Technical design documents and DOC-01.

How do I know if a module is doing too much?

Write its responsibility as one sentence. If the sentence needs the word and, it is two modules. Three secondary signals: it exceeds 500 lines, it imports from more than fifteen internal modules, or it exports more than twelve public symbols. None of those numbers is the rule — they are the smoke alarm that makes you apply the sentence test. See Modularity and separation of concerns.

What is separation of concerns in practice?

Seven concerns must not be mixed: transport (controllers), validation (schema at the boundary), orchestration (a use-case coordinator), business rules (pure functions with no I/O), persistence (repositories), external integration (clients with timeouts), and observability (an injected structured logger). The most common violation is business rules living in a controller, which makes them untestable without an HTTP server. The second most common is a database call inside a calculation. See Modularity.

What is a circular dependency, and how do I fix it?

Module A imports B, and B imports A. It is never a naming problem; it is a missing third module C that both should depend on. In the worked example that module is contracts/quoteTypes.ts, which holds the shared vocabulary and imports nothing, so it cannot participate in a cycle. Enforce it in CI with a dependency-graph rule rather than by vigilance.

What is an ERD, and why does the data model deserve a diagram?

An entity-relationship diagram shows the tables, their columns and keys, and how they relate. It earns its place because the data model is the hardest thing to change later — code can be rewritten in a sprint, a schema with two years of production data in it cannot. The diagram is also where idempotency becomes real: DOC-01 Figure 6 shows a unique constraint behind every replay guarantee, which is what makes the guarantee hold under concurrency rather than only in the happy case.

What is a sequence diagram for?

It shows the order of calls across components for one flow, with timeouts and returns. Its real value is that it makes the latency budget visible and forces you to decide what happens at each step when the call does not come back. Draw the degraded path, not the happy one — the happy path is the one everybody already imagines correctly. DOC-01 Figure 7 deliberately shows a model timeout falling through to the heuristic.

Contracts and code quality

What is the difference between an interface and a contract?

An interface is the shape — names and types. A contract is the shape plus five promises: inputs (types, units, ranges), outputs (exact shape and units), errors (the enumerated, named failures and which are retryable), side effects (what changes and under which idempotency key), and timing (latency budget and timeout). An interface without those five is a suggestion. See Interfaces and contracts.

How do I know if a contract is strong enough?

Ask: could someone change this module's behaviour in a way that damages a caller, while every test still passes? If yes, the contract is decorative. A contract is only real when breaking it breaks a test. In the worked example the guards are UNIT-16 (the 5-to-75 minute clamp) and INT-09 (a replayed key returns the same quote and creates no second row).

Why does the guide insist on units in names?

Because number and number compile fine whether one of them was seconds and the other minutes. No type system catches it; a whole family of production incidents comes from it. prepSeconds, totalCents, quotedReadyMinutes — never a bare duration, amount or time. This is a blocking check in DOC-04 (CR-07) precisely because it is cheap to enforce and expensive to miss.

What is a magic number, and why does it matter so much?

An unexplained numeric literal in the code — t = t * 1.15 + 180. The cost is not aesthetic. In six months nobody can say where 1.15 came from, so nobody dares change it, and the policy it encodes becomes frozen by fear. The fix is a named constant with a comment citing the source and date: "Ops study 2026-03, table 4". See the buffer-policy pair in Good code vs bad code.

What is a branded type?

A string or number type tagged so the compiler refuses to interchange it with another of the same primitive: type QuoteId = string & { readonly __brand: 'QuoteId' }. It prevents passing a correlation ID where an idempotency key is expected — a bug that plain string types permit silently and that no test will find unless you thought to write it. See DOC-02 section 3.

When should code carry a comment?

Comment the why, the constraint, or the domain fact. Never the what — the code already says what, and a restating comment goes stale and then lies. The highest-value comments in a codebase record measured domain knowledge with its source: "Fryer batching: orders with any fried item wait for the next basket cycle. Measured mean across the estate is 90 s (Ops study, 2026-03)."

What does DRY actually mean?

Not "never type the same characters twice" — that reading produces bad abstractions. It means every piece of knowledge has one authoritative home. The 5-minute pickup floor appearing as a literal in three places is a real violation. Two validators that both happen to check for a non-empty string are not; merging them couples unrelated rules. Practical threshold: two occurrences may be coincidence, three is a pattern worth extracting. See DRY and SOLID.

Which parts of SOLID actually matter?

S (single responsibility) and D (dependency inversion) carry nearly all the practical value, and they compound: S makes a module comprehensible, D makes it testable. L (substitutability) becomes critical the moment you have a fallback implementation — a fallback returning minutes where the primary returns seconds is a sixty-fold defect no compiler catches. O and I are worth knowing so you can name a smell, not worth restructuring working code to satisfy.

Failure handling and idempotency

What is idempotency, and why is it non-negotiable?

Running the same operation twice with the same inputs produces the same end state, with no duplicate side effects. It is non-negotiable because duplicates are not rare: networks retry, users double-tap, queues redeliver, cron jobs overlap. A script that works the first time and breaks the second is broken, not fragile. The mechanism is an idempotency key checked before the side effect fires, with a database unique constraint behind it — the application check alone loses the race under concurrency.

Why does every external call need an explicit timeout?

Because a call with no timeout can hang forever, and a hanging call holds a connection. Enough of them exhaust the pool and take the service down without a single error being logged — the outage presents as a slow page, which is the hardest kind to diagnose. This is a blocking check (CR-16) and no exception is granted. State the number; do not rely on a library default you have not read.

What is a circuit breaker?

A counter that stops calling a failing dependency. After N failures in a window it "opens": subsequent calls fail immediately without touching the network, which stops you from adding load to something already struggling and stops your own latency from collapsing. After a cooldown it half-opens and admits one probe. In PTPS: 5 failures in 60 seconds opens it, 120 seconds of cooldown, one probe to close. See DOC-02 section 5.5.

Why is an empty catch block treated as a production defect?

Because it converts a loud, diagnosable failure into a wrong answer. In the worked example, swallowing a KDS error leaves the load undefined, the next line computes NaN, and the guest is told their order will be ready "in about NaN minutes" — with every symptom appearing downstream of the cause. If a failure is genuinely ignorable, the catch must say so in a comment and still log at debug level.

What is the outbox pattern?

Instead of writing to the database and then publishing an event — two operations that can partially fail — you write the event as a row in an outbox table in the same transaction as the business data. A separate process drains the outbox and publishes. The guarantee becomes at-least-once, so consumers must dedupe, and the contract says so plainly rather than letting consumers assume exactly-once. See DOC-02 section 5.9.

Should I ever default a missing value?

Almost never in a service path. load ?? 1.0 looks defensive and is the opposite: it tells an idle kitchen and a kitchen at four-times capacity apart, badly, and quotes both the same. A missing required value means a dependency is broken, and the correct behaviour is a classified error that someone can act on. Defaults belong at genuine configuration boundaries, documented, not sprinkled through logic.

Testing

What is the testing pyramid?

A target distribution: roughly 70 percent unit (pure logic, milliseconds, no I/O), 20 percent integration (two or more real components across a boundary, seconds), 10 percent end-to-end (critical journeys through the real interface, minutes). The rule that makes it work: push every assertion as far down as it will go. An inverted pyramid produces a suite that is slow, flaky and distrusted, which is functionally the same as no suite. See The testing pyramid.

What is the difference between a unit test and an integration test?

A unit test exercises one piece of logic with no I/O — the clamp function, the buffer table, the basket arithmetic. An integration test exercises a real boundary: route plus schema plus repository plus a real database, with external systems stubbed. The tell is the runtime: if it needs a container to start, it is an integration test. The corollary is that most business rules should not require a container, and if they do, the rules are in the wrong layer.

How do I tell a good test from a bad one?

Four questions. Does its name state the rule it protects? Does it assert an output or observable behaviour rather than a mock call count or private state? Would it survive a refactor that preserves behaviour? Would it fail if you deliberately broke the rule? A test asserting expect(r).toBeDefined() fails all four. The last question is the decisive one, and it takes ninety seconds to check — see DOD-A3 in DOC-07.

Is test coverage a useful metric?

Coverage on new and changed lines is useful and is a merge gate at 80 percent. Total repository coverage is a vanity number: it is dominated by legacy code, moves glacially, and drives tests written to raise a percentage rather than to reduce risk. Coverage measures which lines ran, never whether anything was asserted — which is why 94 percent coverage with toBeDefined() assertions is worse than 70 percent with real ones, because it also produces false confidence.

What are the four mandatory test types per feature?

Happy path (documented usage works), failure path (dependency down, slow, or returning nonsense), boundary cases (empty, maximum, one-over-maximum), and idempotency (running twice leaves the same state and fires no duplicate side effect). A feature with only happy-path coverage is incomplete and does not meet the Definition of Done. In DOC-05, failure cases outnumber happy-path cases 28 to 20 — correct for a system wrapping an unreliable model.

Git and code review

How big should a pull request be?

Under 400 lines of production code, with a team median of 250. Defect-detection rate collapses beyond roughly 400 lines — a 900-line pull request does not get a review, it gets an approval. PR size is the strongest single lever on review quality: cap it and detection rises with no other intervention. With AI generating code the pressure runs the other way, and holding the cap is the architect's job.

What should a commit message contain?

An imperative subject under 72 characters, then a body explaining why — the diff already says what. Then trailers: the requirement ID, the test IDs, and any assumption made. In nine months that message is the only surviving explanation of the change, and git blame on a strange line should surface a reason rather than a shrug.

What does a reviewer actually look for, in order?

Four questions, in this order: is it correct (including at the boundaries), does it fail safely (timeouts, retries, no silent catches, idempotent side effects), can it be changed (single responsibility, no new cycle, tested behaviour), is it consistent (naming, structured logs, no secrets, no stray any). The classic weak review spends its entire time on question four. DOC-04 turns this into 42 named checks, nine of them blocking.

Directing and approving AI-generated code

How do I prompt for code I can actually review?

Four patterns. Contract first — ask for the interface and contract, correct it yourself, then ask for the implementation of that exact contract. Name the tests — supply the case IDs from the test plan rather than asking for "tests". State the negative space — no new files, no new dependencies, no defensive defaults, do not change the public interface. Ask it to break its own work — an explicit adversarial pass finds more than a review of the same code does. See Directing the AI.

What is the most common defect in AI-generated code?

Reimplementing something the repository already has — a fourth bespoke retry helper with a fifth jitter strategy. It looks fine in any single review and after two months there are four retry policies, three log formats and two definitions of the pickup floor. Second most common: code written for exactly one successful execution, so no idempotency key and no timeout. The two review questions that catch the most are "what happens if this runs twice" and "what happens if the call on line N never returns."

What should I never approve?

Nine blocking findings from DOC-04: a new any without justification; an unvalidated inbound boundary; a value with a unit missing from its name; an outbound call with no timeout; an empty catch; a side effect with no idempotency key; a secret in code, logs or errors; a protected route without an ownership check; a missing correlation ID; and a new external boundary with no failure-path test. Blocking means request changes — not a comment, not a follow-up ticket.

Can the AI approve its own code?

No. It can write the code, write the tests, and find its own defects — often better than a tired human. It cannot approve, because approval is an accountability act and accountability cannot be delegated to a process with no stake in the outcome. Your signature asserts three things: you found evidence the change does what was asked, you checked the failure paths, and someone can change this code next quarter without fear.

Which engineering KPIs should I report upward?

Four, because they are two speed measures and two stability measures and gaming one shows up in its pair: deployment frequency, lead time for change, change failure rate, and time to restore service. Add two quality measures with real signal: escaped defects per sprint, and coverage on new and changed lines. Never report lines of code, commits per engineer, story points delivered, or total repository coverage — each of those rewards behaviour you do not want. See Engineering KPIs.

What is technical debt, and how is it different from a mess?

Debt is a deliberate, recorded decision to ship something suboptimal in exchange for time, with the interest understood: named, quantified, owned, ticketed, with a repayment trigger. A mess is the same code with none of those properties. The distinction is operational, not semantic — debt can be prioritised because someone can state the cost of leaving it. A mess cannot, so it gets discovered as a bug. See Technical debt.

What if I don't understand the code the model produced?

Then it is not approvable, and that is a complete answer — DOD-21 requires that a junior developer could understand the change from the code, the contract comments and the PR description alone. Ask for it in smaller pieces, ask for the contract separately, or ask the model to explain the specific lines and then verify the explanation against the code. What you must not do is approve on the strength of the code looking confident. Confident-looking is what generated code always is.
