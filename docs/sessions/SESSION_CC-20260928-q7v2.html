STORY-005's, STORY-006's and STORY-014's suites pass UNMODIFIED.
Notes
SIX POINTS. (1) NO RATE CARD IN THE BACKEND, AND THAT WAS THE MAIN DESIGN CALL. mcp/trip-quotes/server.py already holds one (PRICE_BOOK, season multipliers, add-ons). Porting it to JavaScript would have created a SECOND SOURCE OF TRUTH FOR MONEY, and the two would disagree the first time one was updated - the worst kind of pricing bug, because both sides look authoritative. Instead an advisor composes a quote from explicit line items and the quote records what was priced, so it is reproducible from its own contents rather than from whatever the rate card said that day. A later story wanting catalog pricing should CALL the MCP tool and feed its output in as line items. (2) TWO ENDPOINTS, NOT ONE THAT STRIPS FIELDS BASED ON WHO ASKS. /api/quotes/:id and /api/portal/quotes/:id are different paths, different permissions, different projections; the customer route does not even import internalQuoteView. A single endpoint with a conditional inside is one inverted boolean away from showing a customer the margin on their own holiday, and that inversion is invisible in review. Both projections live in ONE file on purpose - "what exactly does the customer not see?" is a question you answer by reading them side by side. (3) AN ALLOW-LIST, NOT A DELETE LIST, AND THE TEST IS WHAT MAKES THAT REAL. The tempting version copies the record and strips the internal bits; it fails silently the day someone adds supplierRef to a line, and retroactively, for every quote. So the customer document is built field by field and there is a regression test that ADDS netRateAgreementCents and a line-level supplierRef to a stored record and asserts neither appears. Second line of defence: quotePricing nests every internal figure under an internal key, so a careless future edit has to type that word to leak anything. (4) AN UNAUDITED QUOTE MUST NOT EXIST, WHICH FORCED A COMPENSATING ACTION. Save-then-audit breaks the project guardrail the moment auditing fails: a live quote with no record of who issued it. So a failed audit UNDOES THE WRITE - delete for a create, restore the previous version for a revision - and the caller is told it was not saved, which is true. The asymmetry is deliberate and documented: a REFUSAL that failed to audit is logged and does not change the caller's outcome, because a refusal already left the system exactly as it was. Related trap, the same one CC-20260928-4k7p hit on STORY-014: audit entries key on <quoteId>:<event>.v<version>, because keying on the quoteId alone would let first-write-wins keep the creation and silently discard every revision. (5) THE WRITE IS READ BACK BEFORE IT IS CALLED A SUCCESS, and quoteWriteGuard.js exists because of CLAUDE.md's 500-line ceiling. quoteStore.js hit 559 lines on first draft; the split follows a real seam (the quote LIFECYCLE next door, the audit GUARANTEE here) rather than a line count, and it is proven to be a pure move by quoteStore.test.js passing unmodified across it. The read-back compares the VERSION as well as presence, so a store that kept the old row is caught too. (6) NOT DONE, DELIBERATELY. No group pricing or per-traveler units - STORY-008 owns group travel and this story must leave room for it, not pre-empt it. No draft or withdrawn statuses: each implies a visibility rule nobody has specified, and an unspecified visibility rule is worse than none. No currency change on a revision (it would reinterpret every figure without changing one), no taxes or fees (no jurisdiction model exists), no multi-currency within one quote (rejected outright rather than summing unlike currencies), no PDF rendering, no quote expiry, and no delete route - a quote is evidence of what was offered. Reads are not audited, only generations, modifications and refusals. CONCURRENT EDITS TO ONE QUOTE ARE LAST-WRITE-WINS: two advisors saving the same quote in the same second needs row locking, which needs the database - the same pre-existing repo-wide limit documented in jsonFileStore.js. CI green on a clean machine for e87c402 - both jobs, Run tests and Typecheck, confirmed via the Actions API, which is the first INDEPENDENT confirmation of this story's results. The six cases: a quote and its audit entry both survive a restart with the price intact; a REVISION survives (v2 at 900000, not a reverted v1); the REHYDRATED record still renders without costs; both events are in the persisted trail correctly attributed; a retry after a restart is still a replay and not a second quote; and an unauditable quote rolled back by quoteWriteGuard is gone from quotes.json itself, not merely from one process's Map.
Notes
FOUR POINTS. (1) THE GAP WAS REAL, NOT THEORETICAL, AND I SHOULD HAVE CAUGHT IT IN THE FIRST PASS. Every other quote suite runs with COLABERRY_DATA_DIR unset, which is in-memory. The story's named failure path is "quote not saved" and quoteWriteGuard reads every write back before calling it a success - yet none of that had ever met a file, and an in-memory Map reads back perfectly from a store that would have lost the row on disk. Same reasoning and same shape as roleAssignments.durability.test.js, which exists for the identical reason on STORY-006. (2) THE REVISION CASE GETS ITS OWN TEST BECAUSE THE FAILURE IS SILENT. A lost CREATE is loud - the advisor cannot find the quote and re-issues it within the hour. A lost REVISION leaves a normal-looking quote at the superseded price, so the business ends up arguing with a customer about what it offered them, with an audit trail that says one thing and a quote book that says another. (3) THE REHYDRATION ASSERTION EARNED ITS PLACE AND WAS NOT IN THE ORIGINAL PLAN. The stored row is serialized and reparsed between processes, so re-running the leak scan on the reloaded record proves customerQuoteView filters a plain JSON object - not merely the frozen object priceQuote happened to return. The in-process tests could not distinguish those two. (4) THE ROLLBACK-TO-DISK CASE WAS THE ONE GENUINELY AT RISK. quoteWriteGuard undoes an unauditable write with store.delete; in memory that is a Map delete, and if jsonFileStore had not persisted deletions the row would have been absent from the writing process and present in the JSON for the next process to load - the guardrail violated with extra steps. It passes: the file is verified empty by reading it raw. STILL NOT TESTED: concurrency. generateQuote and modifyQuote contain no await, so Node cannot interleave two calls and they are atomic by construction - but that is a guarantee held up by nothing except how the functions happen to be written, which is exactly the fragility adminConcurrency.test.js was written to defend on STORY-006. A structural assertion plus a real HTTP race is the next thing worth doing here.
