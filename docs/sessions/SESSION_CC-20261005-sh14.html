Notes
SIX POINTS. (1) THE CENTRALISED BOOK WAS NOT BUILT, BECAUSE IT ALREADY EXISTED. crm-transactions is the one durable store every booking path writes to - one row per trip from bookTripService, one row per group MEMBER from groupBookingService carrying a groupId. bookTripService keeps its confirmed single bookings in an in-memory Map that does not survive a restart, so that ledger row is their only durable trace: reading it is not the convenient source, it is the only one still correct tomorrow. The board reads it LIVE on every call - no projection, no cache, no overnight job - which is what makes "dashboard fails to display new bookings" structurally hard rather than merely tested. (2) THE STATUS IS AN OVERLAY, NOT A COLUMN. logTransaction is deliberately idempotent by returning the existing row untouched, so the ledger cannot be updated through its own front door - a ledger that rewrites its rows is not a ledger. The overlay holds status, previousStatus, version and who/when, and NO customer, itinerary or money, so it cannot drift. The rejected alternative - copy every booking into our own table with a status column - buys a simpler query and costs a sync step that can fail, which is the exact failure path above. A booking with no overlay row is UNTOUCHED, not missing, and reads as confirmed. (3) THE VERSION IS WHAT MAKES "ALL CHANGES ARE LOGGED" TRUE. auditedCommit keys entries on id + .vN, and the audit log is first-write-wins: keyed on the tripId alone, the first status change would be recorded and every later one SILENTLY DISCARDED - the code would pass its other tests while quietly failing the trust criterion. (4) A SIXTH ROLE, NOT A GRANT ON AN EXISTING ONE. admin was refused because the role that reads the audit trail must not also be the role that can cancel a booking; sales because the board is every customer's booking at once, strictly wider than the relationship-scoped read CRM_CUSTOMERS_READ was argued for. The READ is the dangerous half here (every booking the agency holds, in one response) while the WRITE only walks a four-state lifecycle - the opposite of the usual intuition, and why the split matters. The role deliberately does NOT hold admin.audit.read, the CRM grants, or any write on products, packages, quotes or proposals. (5) ONE CORRECTION MADE DURING THE WORK: a comment claiming the metrics endpoint is /api/ops/metrics was wrong - it is /api/admin/metrics (only its PERMISSION is named ops.metrics.read) - and was fixed rather than left; nothing was broken by it. A test assumption was also wrong on first run: deriveAuditKey refuses only a BLANK or non-string base, not a short one, since the event discriminator it appends already clears the minimum length - the test now pins both sides of the real boundary. (6) NOT DONE, DELIBERATELY: no query-string filters on the list route - listBookings takes status and groupId and they are tested, but nothing in this pipeline reads query strings (server.js parses the pathname only, and no route in the system takes one), so exposing them means editing the central request pipeline every route shares for something no acceptance criterion asks; no on_hold status (a state invented ahead of the requirement asking for it is a state nobody can say is correct - one entry in STATUSES and two transition rows when one does); no bulk status endpoint (each change is its own audited decision); no delete route (that is what cancelled is for); and single-trip bookings were NOT made durable - that is a pre-existing limitation of the booking path this story reads around rather than fixes.
