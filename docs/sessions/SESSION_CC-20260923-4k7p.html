STORY-006: role-based permissions — a permission table, an admin surface, and an audited role-assignment path

AC-2: customer and advisor tokens get 403 on every admin path while still reaching their own routes, AND an admin gets 403 on both /api/portal/trips and /api/advisor/reviews. AC-3: the role change, the denied access attempt and the refused assignment are all readable through GET /api/admin/audit with actor, resource, required permission and correlation id. Sharpest test: a customer logs in, is promoted by an admin, and on the SAME session token with no new login the advisor queue opens and their own trips close.
Notes
FIVE POINTS. (1) hasRole() WAS DELETED, NOT DEPRECATED. Leaving it exported "in case" means two ways to make an access decision, and the first route that picks the wrong one is a hole nobody sees — the same reasoning auth.js already used to keep both credential kinds in one authenticate(). Single call site, so the deletion was clean. (2) NO ROLE INHERITANCE, AND ADMIN IS NOT A SUPERUSER. Each role's grants are written out longhand and admin deliberately lacks portal.trips.read and advisor.reviews.read; tests assert those ABSENCES so a later "simplification" into a hierarchy fails loudly. Inheritance is how privilege creep happens: add a permission to customer for a good reason and every inheriting role silently gains it. (3) ROLES RESOLVE PER REQUEST, NOT AT LOGIN. A session issued before a demotion gets the current role on its next call. Resolving at login would mean a demotion does not bite until the session expires, and with a 12-hour absolute lifetime that is not revocation. (4) DELIBERATE ASYMMETRY ON AC-3, and it is the one place the criterion was read rather than followed literally: 403s get a durable audit row, 401s do not. A 401 is anonymous — no actor to attribute it to — and the audit store rewrites its whole file per row, so auditing them hands any unauthenticated caller a disk-fill with quadratic write amplification. 401s remain fully recorded in the structured log stream; they are simply not in the evidence store. (5) TWO GUARDS ARE UNREACHABLE OVER HTTP AND WERE KEPT ANYWAY. assignRole's not_permitted never fires through the API because the route's own permission check refuses first, and last_admin never fires because the only caller who could demote the final admin is that admin, whom self_assignment stops first. Both are live on the direct-call path a script would use, which roleAssignments.test.js exercises. A guard reachable by only one route must not be deleted because the other route happens to be covered — recorded here so a future reader does not "clean up" dead code that is not dead. SEPARATELY: the startup route guard has its own test against all three malformed shapes, because without it the guard could be deleted and every other test would still pass — it only ever runs against a route table that is already valid. NOT DONE, deliberately: per-resource scoping ("advisor for THESE customers"), time-bounded grants, approval workflows, bulk assignment, and audit-trail filtering by actor or date (needs query-string parsing, which the pipeline does not do). Advisor-on-behalf-of-customer access stays unbuilt and is a separate explicit permission when wanted, not a side effect of seniority. OBSERVED, NOT FIXED, OUT OF SCOPE: request_handled logs outcome: "success" even for a 401 or 429, because log() derives outcome from level rather than status — misleading to anyone reading the stream, and a one-line fix for whoever owns that next.

Verification
22/22 npm test (was 20/20), npm run typecheck clean. The mutual-demotion race asserts countAdmins never reaches zero and that the surviving admin still works while the demoted one is refused immediately. Ten concurrent identical promotions produce exactly one assigned, nine unchanged, exactly one authz.role_assignment.changed in the trail and nine unchanged entries. Durability is proven in a SECOND PROCESS: an assignment and its audit rows survive, idempotency survives, a demoted admin stays demoted, the last-admin guard still refuses after a restart, and deleting the store file falls back to directory roles with the audit trail intact.
Notes
FOUR POINTS. (1) A CLAIM IN THE PREVIOUS ENTRY WAS PARTLY WRONG AND IS CORRECTED HERE. That entry records last_admin as unreachable over HTTP. It is unreachable SEQUENTIALLY - self_assignment always fires first - but two admins demoting each other at the same instant does reach it, which the new race test demonstrates. The comment in admin.test.js asserting unreachability has been rewritten rather than deleted, because that exact reasoning is what invites a future reader to remove the guard as dead code. (2) THE CONCURRENCY RISK I FLAGGED DID NOT EXIST, BUT THE FRAGILITY DID. assignRole is synchronous end to end (resolveRole, countAdmins, recordAudit and fs.writeFileSync are all sync), so Node cannot interleave two calls and the read-then-write is atomic by construction. That is a real guarantee held up by nothing but how the function happens to be written: one await inside it and two concurrent mutual demotions both read a count of 2, both commit, and the system lands on zero admins - the one state nothing inside it can recover from. Hence a structural assertion that fires the day someone makes it async, which will trip long before anyone re-reads the race test. (3) THE LOSER'S STATUS CODE IS DELIBERATELY NOT PINNED. It is 403 when the second request had not been authenticated at the moment the first committed - per-request role resolution had already stripped its admin role mid-flight, which is the feature working - and 409 when it had been authenticated and reached the handler. Both preserve the invariant. Asserting one would be asserting the socket scheduler and would go flaky on a differently-scheduled machine, so the test asserts countAdmins === 1 and accepts either refusal. (4) THE DEMOTION DIRECTION GOT ITS OWN DURABILITY TEST FOR A REASON. A lost promotion is a nuisance someone reports within the hour; a lost demotion is a silent re-grant that the audit trail actively contradicts. Related and non-obvious: the last-admin guard is proven to count PERSISTED state rather than the directory, because a fresh process rebuilding the count from the environment alone would see two admins and demote the remaining one to zero. The documented recovery path is now proven rather than asserted in a comment - a lost store falls back to directory roles - and the test records the honest cost in its own assertion: that fallback UNDOES EVERY DEMOTION. Safe in the sense that the bootstrap admin can still log in and nothing is wedged, not safe in the sense of preserving revocations; re-applying them is what the audit trail (a separate file, proven untouched by the loss) exists for. STILL UNHANDLED, pre-existing and repo-wide: two Node processes sharing a data directory each hold their own in-memory Map and lose each other's writes. Documented in jsonFileStore.js; the real fix is Postgres. NOT VERIFIED BY CI — the push was denied by the permission layer, so every result above is local.
