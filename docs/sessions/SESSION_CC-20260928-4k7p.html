Notes
SIX POINTS. (1) CRITERION 2 NEEDED NO NEW STATE, AND THAT WAS THE MAIN DESIGN FINDING. booking/crmTransactionLog.js — despite the misleading name, a booking-transaction log, not a CRM — is already written by bookTripService at the moment a booking confirms. So the customer half of the CRM is a read model over it and the history "updates" because the history IS the booking log: no sync step, no job to fall behind, no window where the CRM disagrees with what the customer was charged. A CRM bookings table would have been a second answer to "what has this customer bought?", and the second answer is the one that goes stale the first time a booking is amended. portal/itineraryService.js:11 already argued this for the customer-facing view; the sales view gets its OWN projection rather than reusing itineraryView, because that function exists to STRIP internal fields from a customer and sales is the opposite audience. (2) A FOURTH ROLE, NOT A WIDENED ADVISOR — and this was escalated to the user rather than decided quietly, since it is security posture. permissions.js documents "advisor — NOT customer data by default", and granting advisor the CRM would have meant deleting that line to make this story fit. Its header also predicted the alternative ("when a fourth role arrives ... only this table does"). ADMIN DELIBERATELY DOES NOT GET THE CRM: an admin can GRANT sales and that act is audited, but cannot quietly read the lead book — granting yourself access leaves a record, which is the whole difference between an admin and a superuser. Read and write are split so a future reporting integration can read without editing; crm.customers.read is split from both because a booking history is more sensitive than an enquiry. (3) THE FIRST-WRITE-WINS TRAP, WHICH IS THE SUBTLEST THING IN THIS STORY. auditLog.js:213 warns that a caller keyed on its own business id alone will have its SECOND distinct event silently discarded. Keying lead edits on <leadId>:updated would therefore have recorded the first edit to a lead and lost every later one — a trail that looks complete and is not, which is worse than no trail. EDITS key on the per-request correlationId; CREATES key on the freshly generated leadId, collision-free by construction. There is a regression test that makes two successive edits and asserts both entries exist and differ. The consequence is stated as a rule: a mutation arriving with no correlationId is REFUSED rather than performed unaudited, because if the guardrail is that all changes are audited then "I cannot audit this" has to mean "I will not do this". (4) VALIDATION IS SPLIT ON THE LINE adminRoutes.js:98 ALREADY DREW. The route checks only the envelope ("is this a JSON object?"); the service judges the fields. Rejecting a malformed email at the boundary would return the same 400 while quietly losing the audit entry — a refused lead that leaves no trace. So a non-object body is invalid_request_body and never reached a decision, while a bad email is invalid_lead, audited, and reported with EVERY problem at once rather than one per round trip. The audit entry does not echo the rejected value back, and there is a test asserting "carrier-pigeon" never appears in the trail. (5) UNAUTHORIZED ACCESS IS HANDLED IN NEITHER NEW MODULE, ON PURPOSE. Routes declare a permission and server.js enforces it once and audits every refusal; a second check inside the CRM would be a second policy that can disagree with the first, which is the reason STORY-006 centralised it. Hence the 5×3 matrix at the boundary — each route names its own permission, so passing one proves nothing about the other four. Also hardened: a malformed percent-sequence in a path id is a 400 rather than an unguarded decodeURIComponent throw, which would be a 500 on a URL a scanner finds within the hour; non-editable fields are refused BY NAME rather than silently dropped (dropping them tells the caller the save succeeded), and the legal half of a mixed patch does not apply either; createdAt/createdBy are outside the allow-list, because an "update" that can rewrite who captured a lead is a way to erase the trail. (6) NOT DONE, DELIBERATELY, AND THE HONEST LIMITS. No cross-customer revenue aggregate — lifetimeValueCents is a per-account relationship figure and revenue analytics is STORY-012's job; two modules computing the business's revenue ends as two different numbers on two dashboards. No customer directory — identity belongs to portalCredentials.js and a CRM copy would be a second truth and a second place to leak a contact list from, so "customer" means "has a confirmed booking" and a person with none is a LEAD, which is a coherent split rather than a gap. No lead deletion ("lost" is a status; erasing a lead erases the audit trail's subject), no conversion flow, no owner assignment, no merge of two leads found to be the same person, no pagination — both list reads are O(n) scans and STORY-016 is the scalability story, so an index (a second copy that can desync) waits for a measured reason. READS ARE NOT AUDITED, only modifications and denials: the criterion is about modification, and an entry per page view buries the entries that record a change; if wanted it belongs at the boundary, once. Mixed currencies on one account are collected into a currencies array so a total across unlike currencies is visible as such rather than quietly wrong, but nothing CONVERTS them. Persistence is still jsonFileStore, so the pre-existing repo-wide limit stands unchanged: two Node processes sharing a data directory each hold their own in-memory Map and lose each other's writes — documented in jsonFileStore.js, and the real fix is Postgres, not something to bolt on inside this story.
