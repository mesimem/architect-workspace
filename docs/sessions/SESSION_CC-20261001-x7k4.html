Notes
FIVE POINTS. (1) FOUR DEFECTS FOUND BY RUNNING IT, NOT BY READING IT, and three were in my own tests. The cardinality test blew the stack: the overflow fold called bucketFor(OTHER_LABEL) to reuse the insert path, and at the cap that bucket does not exist either, so it recursed forever - it failed under exactly the load the module exists to survive. A smoke test then showed failure_rate at 0.25 with nothing broken: the health probe's own 503 degraded was being classified as a 5xx server failure, so a balancer polling through a busy period would have manufactured an outage out of correct behaviour. Probe traffic is now excluded from the aggregate entirely (it also flatters volume and p50, arriving whether anyone is using the system or not) and the rate is 0. Third, the load tests were not generating load: Node's fetch pools connections per origin, so "200 simultaneous requests" were serialised by the CLIENT and queued_total was 0 - every concurrency assertion would have passed while proving nothing, the most expensive kind of green test. Replaced with node:http and an explicit 1,024-socket agent. (2) peak_in_flight IS 1 AND THAT IS CORRECT - the finding worth keeping. Two drafts asserted the wrong thing (first that requests had to queue, then that two had to be in flight together) and both failed against a correct server, because every handler is synchronous once admitted, so on a single-threaded event loop a request runs start to finish without yielding to the next connection. The concurrency is real at the socket level and serialised at the work level BY NODE. So the bound governs AWAITING work and starts to bite the day a handler waits on a database or a supplier API - which is exactly when it is needed and exactly what "thousands of customers" implies. Documented in docs/SCALABILITY.md rather than hidden behind a passing test. (3) 18 OF 2,000 REQUESTS GOT NO RESPONSE, AND IT WAS NOT US. A control run of the identical client against a BARE node:http server produced the same 1982/18 split - the OS accept queue refusing simultaneous localhost connections before any server process sees them. The suite now separates ECONNREFUSED (tolerated, reported, the kernel's and the balancer's layer) from a dropped ACCEPTED connection (fails the build - from a client's side that is indistinguishable from a crash), which makes the test portable instead of tuned to this machine. (4) THE PROBE IS EXEMPT FROM SHEDDING AND THE EXEMPTION IS GUARDED AT STARTUP. A shed probe looks identical to a dead instance, and the instance would never be returned to service because the probe that would report its recovery is the one being refused - a self-inflicted outage. assertShedExemptionsAreSafe throws unless an exempt route is a PUBLIC GET: an exempt write would reach the whole-file-rewrite store with no concurrency limit, walking straight into the bottleneck this story bounds. The public body is held to status and uptime_ms because anything about limits or load on an uncredentialed endpoint is a published capacity map. (5) NOT DONE, DELIBERATELY: Postgres (a database-engine change is a governance boundary under CLAUDE.md and would rewrite every store in the repo - the bottleneck is measured and contained, not removed); multi-process cluster (the store has no file locking, so two workers sharing COLABERRY_DATA_DIR can lose a write - horizontal scale waits on the same database move); an nginx upstream config (untested infra in a repo with no deploy target for it would be documentation shaped like code - the contract is written in docs/SCALABILITY.md instead); per-caller fairness and readiness-vs-liveness probes, both listed in the not-handled section. .colaberry/progress.json has all three criteria passed: true with files_touched/tests_added/notes filled, and verification.state left as in_progress with commit_sha null - same precedent as STORY-010 and STORY-015, since the platform writes those on sync and claiming verified with no SHA would be a claim I cannot back.
