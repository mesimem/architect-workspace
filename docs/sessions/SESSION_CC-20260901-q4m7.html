What changed
the customer portal's authentication, sessions and itinerary view, plus the HTTP boundary work to reach them. New backend/src/services/portal/portalCredentials.js verifies passwords with node's built-in scrypt (N=16384, r=8, p=1, per-user 16-byte salt, cost parameters stored inside each hash so they can be raised later without invalidating existing hashes) - no new dependency, since CLAUDE.md classifies that as an escalation and bcrypt/argon2 are both npm. The plaintext is never stored and the module has NO logging surface at all, so no future edit can put a credential in a log line. New portalSessions.js issues 32-byte base64url tokens and stores only their SHA-256 digest, so the session file on disk is not a list of working credentials; two clocks, a 30-minute idle timeout that slides on every request and a 12-hour absolute lifetime that never slides, with expiry DELETING the row rather than filtering it on read, and a 10-session-per-customer cap (oldest evicted) so a login loop cannot fill the disk with valid credentials. New portalLoginService.js ties them together and owns the audit obligation: every attempt is recorded - success, wrong password, unknown account, malformed submission, and blocked-by-lockout - keyed on a SERVER-GENERATED UUID, never the client's correlation id. Five failures against one identifier inside fifteen minutes locks it for fifteen, checked BEFORE the password so a locked account buys an attacker no scrypt work; unknown identifiers are counted too, so a lockout is not an account-existence oracle. New itineraryService.js is a read model over the existing crmTransactionLog, not a second store. backend/src/http/auth.js now resolves BOTH credential kinds in one function (API token first, then session) so no route can accept one and not the other; its contract changed from principal-or-null to {ok, reason} and the single caller moved in the same diff. server.js gained a public route flag (login is the only public route in the build), a Retry-After header path, and the portal login/logout/trips routes. New scripts/hashPortalPassword.js mints hashes for COLABERRY_PORTAL_CREDENTIALS, reading the password from STDIN and never argv - an argument lands in shell history, in ps output and in any shell-audit log.

Notes
DEFECT FOUND AND FIXED BY ITS OWN TEST, worth recording because it was subtle: the first draft of verifyPassword derived the comparison key at the STORED hash's length rather than the canonical 32 bytes. scrypt's 30-byte output is the first 30 bytes of its 32-byte output, so chopping four characters off a stored hash produced a hash that STILL VERIFIED while comparing fewer bytes - anyone able to corrupt the credential table could weaken the check without breaking it. An unexpected key length is now a flat refusal. THE AUDIT-KEY DECISION IS THE OTHER LOAD-BEARING ONE: the audit log is first-write-wins, which is what stops a retry rewriting history, but keyed on a client-supplied X-Correlation-ID that same property becomes an attack - send every attempt with one id and only the first is ever recorded, silencing the log an attacker is about to fill. Keys are therefore server-side UUIDs and the client's id is carried for tracing only. AN UNAUDITABLE LOGIN DOES NOT SUCCEED: if the audit write throws, correct credentials get 503 and the session minted a moment earlier is revoked, because access we cannot account for is worse than an outage. FILE SPLIT FORCED BY THE MODULAR COMPOSITION RULE: server.js reached 561 lines, past CLAUDE.md's 500-line hard ceiling, so it was split before the new routes were allowed to stand - endpoints moved to backend/src/http/routes/ (portal, triage, advisor, africa, assembled by routes/index.js) and server.js kept the HTTP mechanics at 348 lines. Raised with the user before doing it, since it touches STORY-003 code; the split is a pure move and STORY-003's unmodified suite is the proof. SCOPE, agreed with the user rather than assumed: REQ-007 says "view and manage", and only the VIEW half is built - read-only itineraries. Cancellation drags in refunds and reversing an accounting entry; change requests are STORY-003's advisor routing. Half-building a mutation path would have been worse than not building one. A stranger's trip returns 404 and NOT 403, byte-identical to a nonexistent trip, because a 403 confirms the trip exists and walking TRIP-1..TRIP-500 would then map every booking in the business. WHY A MISSING PORTAL CREDENTIAL TABLE DOES NOT STOP THE SERVER when a missing COLABERRY_API_TOKENS does: the API-token table protects every route, so without it the only honest behaviour is refusing to boot, whereas the portal table backs one feature and a typo in it must not take the advisor API down. Absent means every login is REFUSED with 503, never allowed - fail-closed with a reduced feature set, not an auth layer degrading to "allow everyone". KNOWN TRADE-OFF: someone who knows a customer id can lock that account out for fifteen minutes. That is the accepted side of the trade against unlimited guessing; the real fix is per-source-IP throttling at the nginx edge. NOT BUILT, deliberately: role-based permissions beyond the two existing roles and advisor-on-behalf-of access (both STORY-006), MFA, password reset and rotation, breach-list checks, refresh tokens, CAPTCHA, notifying a customer their account is under attack, and cross-process session locking (single-process store, needing Postgres like every other store here). Throttle counters are in memory rather than the durable store on purpose - persisting them would mean a disk write per failed attempt, handing an attacker a write-amplification lever, and losing them on restart loses no audit data because the trail is a separate durable store.
