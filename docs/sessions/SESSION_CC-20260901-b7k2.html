What changed
five paced steps, each confirmed with the user before it was made. THE DESIGN HINGE is that the story's three criteria pull in two directions â€” a completed transaction must reach the accounting software, a failed one must not, and ANY transaction must produce an audit entry â€” so one store cannot hold all three: filter failures out and criterion 3 dies, keep them in and criterion 2 dies. Hence two stores and one module that owns both. (1) NEW backend/src/services/audit/auditLog.js â€” append-only, idempotent by auditKey, durable via shared/jsonFileStore.js. First write wins, so a retry arriving with different content cannot rewrite history. Append-only is enforced by the export list rather than by a comment: there is no update or delete, entries are frozen one level deep (Object.freeze is shallow, which would otherwise leave context writable) and reads hand back those frozen objects. recordAudit THROWS rather than returning a status, deliberately breaking this repo's return-failure-as-data convention: every other module can carry on without its dependency, but an unauditable transaction is a compliance hole, so callers must treat it as a refusal to serve â€” the same doctrine africa/interactionLog.js already uses. Credential-shaped context keys are redacted before they reach disk, because context is caller-supplied and persists forever, and nesting is depth-capped. Placed in its own folder, not under accounting/, because REQ-017 says "all transactions AND CHANGES" and STORY-006's permission changes belong here too. (2) NEW accounting/accountingClient.js â€” the boundary. Never throws; every path returns a typed status. Validation happens BEFORE the wire (integer cents only, ISO 4217 currency, ISO 8601 timestamp, bounded memo), a rejected credential is NOT retried (callWithRetry only retries timeouts, so an unauthorized attempt costs exactly one call instead of hammering something that will keep saying no), a hang times out and retries to the cap, and the dedup store is DURABLE rather than an in-memory Set like the advisor notifier's â€” forgetting a paged advisor costs a second page, forgetting a posted transaction costs a duplicate entry in someone's real books. (3) NEW accounting/transactionRecorder.js â€” the only module talking to both stores. The audit entry is written BEFORE the accounting call and does not depend on it, which is what makes criterion 3 hold when criterion 1 cannot: if the API is down or the process dies mid-post, the audit log still says the transaction happened and the missing accounting.post entry tells a reconciler exactly what to check. NO AUDIT, NO POST â€” if the audit write fails we refuse to post, because an entry in someone's books we cannot trace is worse than a missing entry we know is missing. A replayed audit entry deliberately does NOT short-circuit the post, since the previous run may have died between the two. (4) WIRED INTO BOOKING â€” bookTripService.js records every confirmed booking as completed: true (audits + posts) and every declined payment as completed: false (audits, never calls the API). Recording runs last and cannot un-confirm a booking: the payment has already gone through, so the call is wrapped, classified and logged rather than allowed to surface to a customer as a crash. A replay now re-attempts the post, because if the first run confirmed the booking but could not reach the API the books are missing an entry and a replay is the natural moment to fix it â€” it cannot double-post, so the cost when it already posted is one map lookup. unavailable and invalid_customer are NOT recorded as transactions: no money was attempted, so they are pre-transaction validation failures, already covered by STORY-003's advisor routing. (5) PRICING, agreed with the user rather than invented â€” the booking path had no money in it at all (processPayment({customerId}) returned a bare {success: true}), and an accounting integration that posts entries with no amount is not one. AVAILABILITY Sets became Maps carrying priceCents (.has() behaves identically, so every availability check is unchanged â€” additive, not a reshape), processPayment now takes and returns an amount as a real processor does, and the booking records what the processor said it charged rather than what we asked it to charge.

satisfies REQ-004 and REQ-017, the latter also being one of the three project-wide guardrails. NOTHING MAKES A REAL HTTP CALL â€” the default transport appends to an in-memory ledger behind an injected post argument, the same pattern advisorNotifier.js uses, because no accounting vendor is named in the story and this repo holds no credentials; a real client slots in behind that argument with the timeout, retries, auth contract and idempotency all applying unchanged. TWO DEFECTS FOUND WHILE BUILDING, both in my own work and both the same bug class. (a) The accounting audit entry was first keyed on auditKey + ":accounting"; since the audit log is first-write-wins, a post that failed and was later retried successfully would have kept the failure entry forever and silently dropped the recovery â€” an audit trail that cannot record "it failed, then it worked" reads as authoritative while being wrong. The accounting status is now part of the key. (b) The identical trap in the booking path: the existing test legitimately reuses trip-key-0004 for a decline AND a later successful retry, so keying on the bare booking key would have recorded only the decline. Both now derive through one shared auditLog.deriveAuditKey, which also owns the truncation rule for long keys â€” two copies of a key-derivation rule is how they diverge. THE TIMEOUT / DOUBLE-POST PROBLEM IS FLAGGED, NOT PAPERED OVER: a timeout means we stopped waiting, not that the far side did nothing, so a retry could land a second copy; we send transactionId to the transport as an idempotency key so the vendor dedups our retry, and a vendor without idempotency-key support would need reconciliation instead â€” a consequence for whoever picks the vendor. Known limits, documented in each file's header: single currency (multi-currency means FX rates, rounding rules and a reporting currency â€” a story of its own, not a constant); no refund or reversal path; no dead-letter store, since inventing one before there is a real API to fail against would be pretend machinery; no tamper-evidence on the audit log (no hash chain â€” a person with disk access can still edit the JSON, and detecting that needs signing with key management this repo does not have); and single-process dedup, which needs a Postgres unique constraint like everywhere else in this repo. DRIFT FLAGGED, NOT FIXED: mcp/booking-desk/booking.py is a Python port of bookTripService.js whose header says to keep the two in step; it has no prices and no accounting call, so it is now behind.
