Failure paths: an engine that THROWS is refused, audited as a failure and flagged (not retried - a broken engine does not fix itself); one that HANGS times out, retries exactly once and stops (attempts asserted as 2); one returning the wrong SHAPE is a ContractViolation, not a 200 with undefined in it; zero suggestions is a 200 with a message and a real row in the advisor queue; a throwing audit refuses the whole response; a throwing review queue is logged and does NOT lose the audited answer. Notes
SIX POINTS. (1) THE AI MODULE IS DETERMINISTIC, BY A DECISION TAKEN WITH THE OPERATOR BEFORE ANY CODE WAS WRITTEN. CLAUDE.md's core principle is that probabilistic components do not decide production outcomes, REQ-011 asks for suggestions and not for a technology, and a live model would have meant a paid external dependency, a secret, and acceptance tests that cannot be deterministic. What was built instead is a PORT: one function of one argument matching the shape shared/callWithRetry.js wraps, so a model-backed engine drops in at a single call site and inherits the timeout, retries, audit trail and advisor flag without any of them changing. The envelope is already proven against engines that throw, hang and lie about their shape - so the day a remote engine arrives, the hard part is done. (2) A TEST FOUND A REAL RELEVANCE HOLE, AND THE RULE CHANGED RATHER THAN THE ASSERTION. Scoring alone let a customer asking for a BEACH trip in Botswana be answered with a Botswana SAFARI: it took the country credit and cleared the floor on country alone. Stated interests now EXCLUDE on zero overlap. Matching where somebody wants to go while matching nothing they want to do is the plainest form of the irrelevant-suggestions failure path, and it arrived looking like an answer. (3) AN EMPTY LIST IS AN ANSWER, AND PADDING IT WOULD BE THE BUG. A request whose preferences nothing matches returns ZERO suggestions, a 200 with a message, and a row in the advisor queue - not the least-bad safari. There is deliberately no automatic retry with loosened preferences: quietly ignoring a stated budget to fill the list is worse than saying nothing. (4) WHAT GETS FLAGGED, AND WHAT DELIBERATELY DOES NOT. Three conditions only: zero suggestions despite stated preferences, a matched result at or below 0.6 confidence, and an engine error. A popular result is NOT flagged - somebody who stated nothing has not made an uncertain request, and flagging every browse would bury the queue the guardrail depends on, which is the failure mode requestTriageService.js's own header warns about. The review row is keyed sugg:<requestId>, NOT the bare requestId: advisorReviewQueue is first-write-wins and triage already writes to it, so sharing the key would mean a request that was triaged AND asked for suggestions could hold only one of the two flags, with the other vanishing silently. No advisor is paged; the queue row is the source of truth, and paging a human when a browse returns a thin match is how an on-call rota stops being answered. (5) THE AUDIT ROW RECORDS WHICH PREFERENCE DIMENSIONS WERE STATED, NEVER THEIR VALUES, and that absence is asserted. An audit row is append-only and permanent, and a customer's budget does not need to live in one forever to answer the question the log exists to answer. It is kept flat for the same reason STORY-015 digests its itinerary: auditLog truncates past MAX_CONTEXT_DEPTH, so an array of suggestion objects would audit as "<truncated>". If the audit write fails the service REFUSES to serve rather than hand over suggestions it cannot account for - the same posture safariProductStore takes on an unauditable mutation. (6) SCOPE, AND WHAT WAS DELIBERATELY NOT BUILT. API surface only, no UI, as with STORY-007/008/013/015. POPULARITY IS EDITORIAL, NOT MEASURED, and is stated as such in the code: this repo has no view counts or ratings and the booking ledger is empty on a cold start, so deriving a rank from it would read as data while being zero for everything. It is one function (rankFor) to replace when a real signal exists. Suggestions are NOT PERSISTED - only the audit row is - so there is no read route for a customer's past suggestions; the trail is admin.audit.read. No free-text wishes (preferences are a structured object; unstructured requests remain requestTriageService's job), no dates or seasonality (no date model exists here), no party size (it changes the price, not which trips suit, and quotes/ owns price), no personalisation from history, no caching. Interest tagging is literal substring matching against a small explicit vocabulary: it will MISS tags, costing a trip one point, rather than over-tag, which would make every trip match every preference and is the same failure path arriving through the back door. No durability suite for the new modules - the service writes only through auditLog and advisorReviewQueue, both already proven durable in separate processes by STORY-013's suite, and the corpus holds no state of its own. Notes
FOUR POINTS. (1) THE SHELF WAS BARE, AND THAT WAS HIDING A BUG. The system knew about ONE sellable trip - the single complete record in africa/catalogSource.js - so STORY-009's suggestion engine could only ever return the same safari however well it scored. Seeding real inventory immediately caught a false positive the single-trip catalog could not: a FAMILY GAME-DRIVE package was tagged trekking, because its summary mentions elephant herds BENEATH Kilimanjaro. Half the lodges in northern Tanzania advertise that view. A place name is not an activity, so the mountain is out of the keyword list and the verbs (trek, climb, summit, hike, trail) remain - both climbs still tag correctly, asserted. This is the general rule for that vocabulary now, with a named regression case, not a one-off exception. (2) THE SEED GOES THROUGH THE PRODUCT STORE, NOT AROUND IT. Seed data is the most dangerous data in a system: it arrives before anyone is watching and is trusted forever after. Routing it through createSafariProduct means every package is subject to the same rules a product manager's submission is - the itinerary must cover each day once, the price must clear the cost - and every write is AUDITED. A seeded product is indistinguishable from an authored one, so nothing downstream needs a special case. The test that earns its keep is the first one: seed data the store would refuse is a landmine that passes review, passes a plumbing-only test, and fails on a fresh deploy with the error in a log nobody reads. (3) THE RUNNER REFUSES TO RUN WITHOUT COLABERRY_DATA_DIR, and this is the operational point worth knowing. The product book is in-memory otherwise, so seeding from a separate process would write twelve packages, print a cheerful summary, exit, and take the whole catalog with it - the worst kind of failure, because every line of output says it worked. --ephemeral is there for the one-process demo case and says what it is doing. A second bug was caught while exercising it: validateSafariProduct returns a BARE ARRAY of problems, not a {problems} wrapper, so the dry run was reading every package as valid right up until it threw. (4) WHAT THIS IS AND IS NOT. Representative packages written to be realistic in routing, duration and margin - NOT the agency's actual price list; replace this one file when the real catalogue arrives and nothing else changes. Re-running NEVER UPDATES an existing package, deliberately: a product manager's correction must not be silently reverted by a deploy script, so changing a seeded package after the fact is a PATCH, by a person, through the API. The spread is deliberate rather than decorative - an inventory of twelve identical 7-day wildlife safaris would let the engine pass every test while being unable to tell two customers apart, which is why the interest cover is asserted rather than trusted. .colaberry/progress.json deliberately untouched: this is inventory, not a story, and an invented criterion there would be discarded.
