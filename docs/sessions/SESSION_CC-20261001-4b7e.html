Notes
SIX POINTS. (1) THE AI MODULE IS DETERMINISTIC, BY A DECISION TAKEN WITH THE OPERATOR BEFORE ANY CODE WAS WRITTEN. CLAUDE.md's core principle is that probabilistic components do not decide production outcomes, REQ-011 asks for suggestions and not for a technology, and a live model would have meant a paid external dependency, a secret, and acceptance tests that cannot be deterministic. What was built instead is a PORT: one function of one argument matching the shape shared/callWithRetry.js wraps, so a model-backed engine drops in at a single call site and inherits the timeout, retries, audit trail and advisor flag without any of them changing. The envelope is already proven against engines that throw, hang and lie about their shape - so the day a remote engine arrives, the hard part is done. (2) A TEST FOUND A REAL RELEVANCE HOLE, AND THE RULE CHANGED RATHER THAN THE ASSERTION. Scoring alone let a customer asking for a BEACH trip in Botswana be answered with a Botswana SAFARI: it took the country credit and cleared the floor on country alone. Stated interests now EXCLUDE on zero overlap. Matching where somebody wants to go while matching nothing they want to do is the plainest form of the irrelevant-suggestions failure path, and it arrived looking like an answer. (3) AN EMPTY LIST IS AN ANSWER, AND PADDING IT WOULD BE THE BUG. A request whose preferences nothing matches returns ZERO suggestions, a 200 with a message, and a row in the advisor queue - not the least-bad safari. There is deliberately no automatic retry with loosened preferences: quietly ignoring a stated budget to fill the list is worse than saying nothing. (4) WHAT GETS FLAGGED, AND WHAT DELIBERATELY DOES NOT. Three conditions only: zero suggestions despite stated preferences, a matched result at or below 0.6 confidence, and an engine error. A popular result is NOT flagged - somebody who stated nothing has not made an uncertain request, and flagging every browse would bury the queue the guardrail depends on, which is the failure mode requestTriageService.js's own header warns about. The review row is keyed sugg:<requestId>, NOT the bare requestId: advisorReviewQueue is first-write-wins and triage already writes to it, so sharing the key would mean a request that was triaged AND asked for suggestions could hold only one of the two flags, with the other vanishing silently. No advisor is paged; the queue row is the source of truth, and paging a human when a browse returns a thin match is how an on-call rota stops being answered. (5) THE AUDIT ROW RECORDS WHICH PREFERENCE DIMENSIONS WERE STATED, NEVER THEIR VALUES, and that absence is asserted. An audit row is append-only and permanent, and a customer's budget does not need to live in one forever to answer the question the log exists to answer. It is kept flat for the same reason STORY-015 digests its itinerary: auditLog truncates past MAX_CONTEXT_DEPTH, so an array of suggestion objects would audit as "<truncated>". If the audit write fails the service REFUSES to serve rather than hand over suggestions it cannot account for - the same posture safariProductStore takes on an unauditable mutation. (6) SCOPE, AND WHAT WAS DELIBERATELY NOT BUILT. API surface only, no UI, as with STORY-007/008/013/015. POPULARITY IS EDITORIAL, NOT MEASURED, and is stated as such in the code: this repo has no view counts or ratings and the booking ledger is empty on a cold start, so deriving a rank from it would read as data while being zero for everything. It is one function (rankFor) to replace when a real signal exists. Suggestions are NOT PERSISTED - only the audit row is - so there is no read route for a customer's past suggestions; the trail is admin.audit.read. No free-text wishes (preferences are a structured object; unstructured requests remain requestTriageService's job), no dates or seasonality (no date model exists here), no party size (it changes the price, not which trips suit, and quotes/ owns price), no personalisation from history, no caching. Interest tagging is literal substring matching against a small explicit vocabulary: it will MISS tags, costing a trip one point, rather than over-tag, which would make every trip match every preference and is the same failure path arriving through the back door. No durability suite for the new modules - the service writes only through auditLog and advisorReviewQueue, both already proven durable in separate processes by STORY-013's suite, and the corpus holds no state of its own.
