Notes
SIX POINTS. (1) ALL-OR-NOTHING IS STRUCTURAL, NOT DEFENDED. "Confirms the booking for all members" is not a loop writing a row per traveller - a loop succeeds four times and fails the fifth, and now some of the group is flying and some is not. The whole group is a SINGLE record with a single status and the members are a field on it, so there is only one thing to confirm and partial confirmation is not a state the code can reach. Same reason the payment is ONE charge to the organizer: N charges can partially succeed, which is the same problem wearing a different hat. (2) THE CRM ROW CARRIES EACH MEMBERS SHARE, NOT THE GROUP TOTAL, AND THIS IS THE TRAP WORTH KNOWING ABOUT. crm/customerRecord.js:122 sums amountCents across booking-log rows into a lifetime value. Writing the group total onto every members row would multiply the groups revenue by its size across the whole CRM - a three-person safari reading as three safaris sold on every sales dashboard. So the booking log gets the share (what did this person travel on) and accounting gets the total once against the organizer (what money actually moved). MUTATION-TESTED: swapping perPersonCents for totalCents fails the suite with the named assertion, so the test cannot go quietly green. (3) TWO REAL DEFECTS WERE FOUND BY THE TESTS, NOT BY REVIEW. First, a duplicate memberId went UNREPORTED whenever the earlier member was broken for some other reason: ids were recorded only once a whole member passed, so a blank name freed the id and the organizer learned about the duplicate only after fixing the name and resubmitting - the second round trip the validator exists to avoid. Second, an over-long name was refused with the message "fullName is required" when a name had very much been supplied, sending the organizer hunting for an empty box; "absent" and "too long" are now different prompts, as a module-wide rule. Both are named regression cases. Note the deliberate non-fix: an over-long name is REFUSED rather than truncated, because a shortened name on an airline ticket does not match the passport at the gate - length-capping is fine for a note and wrong for a person. (4) AN UNAUDITED GROUP MUST NOT EXIST, so a failed audit DELETES the row and the caller is told no member was booked, which is true. Same guarantee and same compensating action as quoteWriteGuard.js, and the write guard was split out for the same reason: the service came in at 599 lines, over CLAUDE.mds 500 hard ceiling, and the seam is real (the booking LIFECYCLE next door, the audit GUARANTEE here) rather than a line count. The service is still 482 lines - under the hard ceiling, over the 300 soft target, and stated as such rather than claimed as a pass. (5) DURABILITY WAS PROVEN IN SEPARATE PROCESSES, not assumed - STORY-007 had to learn this after the fact and this story does not repeat it. The case genuinely at risk was the on-disk rollback: the guard undoes an unauditable write with store.delete, which in memory is a Map delete that always works, but had jsonFileStore not persisted DELETIONS the row would be absent from the writing process and present in the JSON for the next process to load - a confirmed group with no audit entry, materialising on the next deploy, with every in-memory test still green. MUTATION-TESTED against a jsonFileStore whose delete does not reach disk; the suite fails. Its counterpart is also covered and is the half usually forgotten: a rollback is only correct if the key STILL WORKS afterwards, or it has traded an unaudited booking for a group that can never be made at all. The retry-after-restart case matters most in money terms - the idempotency record lives on the stored row, so losing it means an organizers retry charges one card for the whole group a second time. (6) NOT DONE, DELIBERATELY. NO HTTP ROUTE AND NO NEW PERMISSION: the booking domain is fronted over MCP, not HTTP - bookTripService from STORY-005 has no route either - and nothing in REQ-010 or the criteria asks for an endpoint, so permissions.js and routes/index.js are untouched. The ONE change outside this story was approved by the operator first: a one-line priceTrip export, taken over copying the leg sum, because two functions that compute what a trip costs are two functions that disagree the first time either is edited. No group rates (the backend deliberately has no rate card - STORY-007s reasoning), no per-member payment, no adding a member to an existing group, no cancellation or amendment, no per-member itinerary variation (REQ-010 asks for a SHARED itinerary and STORY-009/010 own what comes next). CONCURRENCY IS THE STANDING REPO-WIDE LIMIT, unchanged: two calls racing on one idempotency key, and two processes sharing a data directory, both lose writes - documented in jsonFileStore.js, and the real fix is Postgres, not something to bolt on inside this story.
